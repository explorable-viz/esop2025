\section{Evaluation}
\label{sec:evaluation}

We shall now present a critical evaluation of our approach. Firstly we shall
consider the qualitative benefits of the approach in terms of conceptual
simplicity, and the relative ease of implementation. Secondly, we shall provide
an evaluation of our implementations performance compared to
an implementation of the prior state of the art in this field.

\subsection{Qualitative Evaluation Of Graphical Approach}
\todo{No Need to define backwards semantics}
A key benefit of our approach is in avoiding the need to define a backwards
evaluation function. In prior work in this area -- such as \citet{perera22} -- a
program produced an execution trace. To perform a backwards analysis such as
$\demandR_D$, the developer was forced to implement a separate backwards evaluation
semantics using the execution trace until reaching the program inputs. This approach was laborious, and intimately tied the analysis to the language itself. In contrast,
evaluating a program to a dynamic dependence graph allows us to use a simple procedure to
compute both $\demandR_D$ and $\demandByR_D$, whilst only requiring that the
developer implement the desired dynamic dependence graph once, in the forward
evaluation function. 

\todo{Language Agnostic Approach}
The framework we have set up in this paper is language-agnostic. In \secref{conjugate},
we were able to give the core technical details of the approach without having to
mention the details of the language, or the specific choice of dependency relation.
We contrast this with the previously mentioned point regarding related work,
implementing the approach for a new language, or replacing the dependency relation
requires only modifying one part of a language -- its evaluator -- rather than 
building two functions, and being forced to verify that the forwards and backwards
evaluation functions agree. Instead, once the developr has confirmed that their
implementation of the graph algorithms is correct, they can move on.

\subsection{Benchmarking}

In order to test the performance of our dependency analyses, we implemented the
approach in the language described in \secref{core} in Purescript as a 
language called \OurLang. Benchmarks were run on a commercial laptop, with an
Intel Core i7-10850H clocked at 2.70GHz and 16Gb of RAM. The benchmarks were run
on Google Chrome version 121.0.6167.160 and Javascript runtime V8 12.1.285.28.

We tested the performance of our implementation against the approach employed in
the state of the art in this area. Our benchmarks were designed to answer the
following three research questions:
\begin{itemize}
   \item RQ1: What is the overhead graph construction versus trace construction?
   \item RQ2: How does the performance of \textit{demands} compare when run using the graph or the execution trace?
   \item RQ3: How do the various implementations of \textit{demanded by}, the use of a trace, the direct graph implementation, or the dual of \opName{suffices}, compare in performance?
\end{itemize}

In light of the simplicity of the graphical approach, we consider performance
evaluation a success if our performance is at least competitive with the state
of the art. We expect the construction of a dependence graph to be somewhat more
expensive than constructing a trace, but that our dependency analyses to be more
efficient.

\subsubsection{RQ2: Demands Graphs Versus Traces}
We now compare the performance of the twin implementations in terms of computing
demands. We observe a significant increase in the performance of demands using
the graphical approach. In our matrix examples, we observe an average increase
of approximately 40 times, whereas in the graphical examples, the speedup
is approximately 32 times. We note that the inherently sequential algorithm,
\textit{slicing/dtw/compute-dtw} exhibits a significantly reduced speedup when
compared to the rest of the examples.
