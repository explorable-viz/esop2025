\section{Evaluation}
\label{sec:evaluation}

We now present a critical evaluation of our approach. We start by
considering the qualitative benefits of the approach in terms of conceptual
simplicity and ease of implementation. Then, we provide
an experimental comparison of the performance of our implementation and
that of the state of the art in the field, \citet{perera22}.

\subsection{Qualitative Evaluation of Our Approach}
A key benefit of our approach is avoiding the need to define a backwards
evaluation function. By contrast, in \citet{perera22}, a
program produces an execution trace which is rewound in order to perform a backwards analysis such as
$\demandsR$. Consequently, the developer has to implement a separate backwards evaluation
semantics using the execution trace, which propagates a selected output backwards
until reaching the program inputs. This approach is burdensome since
it requires the forwards and backwards evaluation functions to agree with
respect to the dependency analysis.
Conversely, in our approach, once the dependence graph has been computed, the same procedure
can be used to compute both $\demandsR$ and $\demandedByR$ over the graph.

\subsection{Experimental Evaluation}
In order to test the performance of our approach, we implemented our language
from \secref{core} on top of Purescript, which we used to write a selection of
non-trivial examples that reflect realistic targets of dependency analyses
(\secref{evaluation:choice-of-examples}). We then benchmarked these programs on an
Intel Core i7-10850H 2.70GHz with 16Gb of RAM,
using Google Chrome 121.0.6261.69 and Javascript runtime V8 12.2.281.16. Furthermore,
in order to enable a performance comparison, we also implemented the approach in \citet{perera22}, which uses execution traces.

In an interactive system, performance plays a critical role in a user's experience. Thus, we test the performance of the three main components of the
system with the trace-based approach in \citet{perera22}, which boil down to the following three research questions:

\begin{itemize}
   \item RQ1: What is the overhead of the graph construction versus the trace construction?
   \item RQ2: How does the performance of dependence graph-based \textit{demands} compare against the performance of trace-based \textit{demands}?
   \item RQ3: How do the various implementations of \textit{demanded by} (i.e. trace-based, dependence graph-based using $\demandsAlg{}$, and dependence graph-based using the dual of $\sufficesAlg{}$) compare in performance?
\end{itemize}

\subsubsection{RQ1: Overhead of graph construction vs. trace construction}
We first proceed by comparing the time taken to evaluate a program in the
execution trace approach (\textbf{T-Eval}) with the time taken to evaluate a program with the
dependence graph approach (\textbf{G-Eval}).
Since the graph is a more complex data structure to build compared to the trace,
we expect an increased overhead when evaluating a program and building the graph
compared to evaluating and building the trace.

In \tableref{eval-SpdUps}, we see that, as expected, the evaluation of programs
to their dynamic dependence graph does incur some increased overhead, ranging from
3 to 14 times slower than their trace based counterparts. We report the ratio
of graph evaluation time to trace evaluation time in the third column (\textbf{Eval-Slowdown}).

\subsubsection{RQ2: Graps-based demands vs. trace-based demands}
We now compare the performance of the graphical and trace based implementations
when it comes to the computation of \textit{demands}. We observe a significant increase
in the performance of \textit{demands} using the graphical approach, shown in
\tableref{demands-SpdUps}. We report time taken to compute \textit{demands}
with the trace and graph in \textbf{T-Demands} and \textbf{G-Demands}
respectively.

This increased performance for computing \textit{demands} varies across the
examples, with some examples -- most notably the two linked examples \textbf{bar-chart-line-chart} and
\textbf{stacked-bar-scatter-plot} -- exhibiting a speedup of more than 50, and the lowest
-- the stateful dynamic time warp example (\textbf{compute-dtw}) -- close to a 16 times speedup.
This is still a significant improvement in performance across all of our tested
examples.

We attribute this performance improvement to the fact that the execution
trace approach requires the system to completely rewind the execution of the
original program, in effect evaluating it in reverse. We contrast this with the
current approach, which only needs to traverse the relevant part of the graph.

\subsubsection{RQ3: Implementations of Demanded By}

We must finally investigate the performance of \textit{demanded by}. We must
compare the trace based approach with the graphical approach implemented by
using $\demandsAlg{}$, which we present in \tableref{equivalent-impls} as the
columns \textbf{T-DemBy} for the trace implementation, \textbf{G-DemBy-Dir}
for the graphical implementation using $\demandsAlg{}$, and comparing
relative performance in \textbf{Dir-SpdUp}.

We can also recover \textit{demanded by} from $\sufficesAlg{}$ by taking the
De Morgan Dual, which we also tested. This is presented in \textbf{G-DemBy-Suff}
and we compare its performance against the trace approach in \textbf{Suff-SpdUp}.

In all test cases apart from \textit{compute-dtw} we observe that at least one
of the two possible implementations in the graphical approach performs better
than the trace-based approach.

\subsubsection{Discussion}
We shall now consider the qualitative benefits and the performance results in
conjunction. The performance of evaluation is reduced due to the construction of
the graph being more complex than constructing an execution trace. We weigh that
against the relative ease of implementation, and the fact that evaluation now 
only needs to occur once. The performance gains in computing \textit{demands}
are significant. We argue that the user would only need to perform two or three
interactions with a program output in the graphical approach for the performance
gains to be realized. 

The performance change of \textit{demanded by} is less clear. Despite the fact
that the direct implementation uses the same underlying procedure as \textit{demands},
we do not see as consistent of a performance increase, and indeed in some cases
actually see a refression in performance. The implementation which uses the dual
of \textit{suffices} is somewhat more consistent, but with generall worse performance.
It remains to be seen exactly why this is the case, we conjecture that the structure
of the graph constructed during program evaluation significantly impacts the performance
of an implementation of \textit{demanded by}.

We overall consider our results to be positive, since we find a major performance
benefit in one part of the system, as well as an improvement in the simplicity of
the implementation itself. The mixed performance results of \textit{demanded by}
suggest further research is needed on how the structure of the graph affects the
system performance.
