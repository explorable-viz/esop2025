\section{Evaluation}
\label{sec:evaluation}

We now present a critical evaluation of our framework, comparing with the main alternative approach to
implementation bidirectional program analyses, which uses \emph{evaluation traces}~\cite{ricciotti17,
psallidas18smoke,perera22}. We start by considering the relative developer effort involved in the two
approaches, in terms of conceptual simplicity and ease of implementation. Then we provide an experimental
comparison of our implementation's performance.

\subsection{Qualitative Evaluation of Our Approach}

Here, we consider the relative implementation effort required for our graph approach compared to the trace
approach in \citet{perera22}, hypothesising \todo{?} that our graph one is easier to implement and~maintain.
\todo{Can probably pare these two paragraphs back to a couple of sentences in the introduction to this
section. The claims make sense but I'm not convinced that they constitute a ``qualitative evaluation'' or that
a separate section devoted to these points is needed, given that we don't really do anything to back up the

Firstly, a key benefit of the graph approach is that it avoids the need to implement a backwards evaluation
function.  By contrast, the trace approach requires a bidirectional interpreter: building an execution
\emph{trace} during forward execution, and then rewinding that trace to perform a backwards dependency
analysis such as $\demandsR_{R}$. Hence, the developer has to implement a separate backwards evaluation
semantics using the execution trace, which propagates a selected output back to the program inputs. This
approach is burdensome. The two directions of the interpreter need to be kept synchronised with respect to the
dependency analysis, which makes updating the language difficult as every change requires modifying each
direction in a manner that maintains bidirectionality. Conversely, in our approach, once the dependence graph
has been computed, the algorithm described in \figref{conjugate:algorithms:demands} is used to compute both
$\demandsR_{R}$ and $\demandedByR_{R}$ over the graph.\\
\indent
Secondly, our algorithm for computing $\demandsR_{R}$ and $\demandedByR_{R}$ is language-agnostic (as
described in \secref{conjugate}), meaning that it is not affected by changes in the semantics of the language.
With the trace-based approach, the analyses are implemented as part of (forward and backward) program
evaluation, and hence necessarily depend on the details of the language.

\subsection{Experimental Evaluation}

To test the performance of our approach, we implemented our language from \secref{core} in PureScript. We used
our implementation to write a number of benchmarks that reflect realistic \todo{say we} targets
\todo{targets?} of dependency analyses (\secref{evaluation:choice-of-examples}). PureScript is a natural
implementation language for this work as our focus on visualisations lends itself to building web-based
interfaces \todo{uh?}. Additionally, PureScript is the implementation language used by~\citet{perera22} in
their open-source implementation of the trace-based approach, thus enabling a more fair like-for-like
comparison to our work here \todo{hmm. why not just say we reimplemented/adapted their system?}. We then
benchmarked the implementations on an Intel Core i7-10850H 2.70GHz with 16Gb of RAM, using Google Chrome
121.0.6261.69 and JavaScript runtime V8 12.2.281.16. We instrumented both systems in order to extract
performance numbers.

In an interactive system, performance plays a critical role in a user's experience. We therefore compared the
performance of the graph-based and trace-based approaches by measuring the following:

\begin{itemize}
   \item Q1: Overhead of building a dependence graph versus building a trace
   \item Q2: Performance of graph-based \textit{demands} vs.~ performance of trace-based \textit{demands}
   \item Q3: Performance of various implementations of \textit{demanded by}: trace-based, graph-based using
   $\demandsAlg{}$, and graph-based using the dual of $\sufficesAlg{}$.
\end{itemize}

\noindent We assessed performance according to the guidelines proposed by \citet{nielsen93}:
\begin{itemize}
   \item 100ms: limit for an interaction feeling \emph{instantaneous}
   \item 1000ms: limit for a user's train of thought to remain uninterrupted, although
   they may perceive a delay
   \item 10000ms: limit to keep a user's attention on the system
\end{itemize}
We aimed for the interactive queries to stay as close as possible to the \emph{instantaneous} category
(captured by Q2 and Q3), and for the time taken to evaluate programs (corresponding to Q1) to be within the
limit for keeping a user's attention.

\subsubsection{Q2: Graph-based demands vs. trace-based demands}
In \tableref{demands-SpdUps}, columns \textbf{T-Demands} and \textbf{G-Demands} show the average times taken
to compute \textit{demands} with the trace and graph approaches, respectively. The ratio of graph-based to
trace-based performance is in the last column, \textbf{Bwd-Speedup}.

Overall, we observe a significant speedup in the performance of \textit{demands} using the graph approach,
% ranging from around 14.6x for the dynamic time warp example \textbf{compute-dtw}
from 33x speedup for the \textbf{stacked-bar-chart}, to more than 80x for \textbf{gaussian}. In particular,
every \textit{demands} query using the graph based approach is within the ``instantaneous'' category, whilst
all but two of the examples using the trace approach are in the ``noticable delay'' category. We attribute
this performance improvement to the fact that, in the trace approach, each query involves rewinding the entire
execution of the original program, in effect evaluating it in reverse, regardless of whether all of the trace
is relevant. In the graph approach, each query only traverses the relevant parts of the graph.

\subsubsection{Discussion of the results}
When comparing the performance of the graph and trace approaches, we observe that the only consistent
performance loss for the graph approach is due to the increased cost of evaluating a program to a graph versus
evaluating it to a trace (according to \textit{Q1}). We argue that this overhead is reasonable: the graph
only needs to be constructed once and does not impact subsequent interactions; and program evaluation time
does not exceed the limit for keeping the users attention on the system. Additionally, the fast response times
for \textit{demands} and \textit{demanded by} (according to Q2 and Q3), compared to the trace approach,
translate into quick responses to user queries. This is critical for the interactive exploration of digital
media.

Another notable aspect, which is observed for \textit{Q3}, is the performance of \textbf{G-DemBy-Suff}, which
takes the dual of the $\sufficesAlg{}$ algorithm. In the majority of cases, \textbf{G-DemBy-Suff} performs
significantly worse than \textbf{G-DemBy}. We suspect that the generally bad performance of
\textbf{G-DemBy-Suff} is at least partially caused by the expensive set complement operations performed before
and after applying $\sufficesAlg{}$ \todo{why do we suspect this? couldn't it be because the complement graph
is often much larger?}. Furthermore, while our algorithm for computing \textit{demanded by} is graph
