\section{Evaluation}
\label{sec:evaluation}

We now present a critical evaluation of our approach. Firstly, we
consider the qualitative benefits of the approach in terms of conceptual
simplicity, and the relative ease of implementation. Secondly, we provide
an experimental comparison of the performance of our implementation and
that of the state of the art in the field.

\subsection{Qualitative Evaluation Of the Graphical Approach}
\todo{No Need to define backwards semantics}
A key benefit of our approach is avoiding the need to define a backwards
evaluation function. In prior work in this area -- such as \citet{perera22} -- a
program produced an execution trace. Consequently, in order to perform a backwards analysis such as
$\demandsR_D$, the developer had to implement a separate backwards evaluation
semantics using the execution trace until reaching the program inputs. This approach was laborious since
it required the forwards and backwards evaluation functions to agree with
respect to the dependency analysis.

Conversely, we evaluate a program to a dynamic dependence graph
and defer the specific dependency queries until the graph has been computed.
The developer needs to implement the desired dynamic dependence graph only once,
in the forward evaluation direction. Then, we use a simple procedure to
compute both $\demandsR_D$ and $\demandedByR_D$ over this graph.

\subsection{Experimental Evaluation}
In order to test the performance of our approach, we implemented our language
from \secref{core} on top of Purescript, which we used to write a selection of
non-trivial examples that reflect realistic targets of dependency analyses
(\secref{evaluation:choice-of-examples}). We then benchmarked these programs on an
Intel Core i7-10850H 2.70GHz with 16Gb of RAM,
using Google Chrome 121.0.6261.69 and Javascript runtime V8 12.2.281.16. We
also implemented a variant of prior approaches that use execution traces, in
order to enable a like-for-like performance comparison.


In an interactive system, performance plays an enormous role in the experience
of a user. We have to test the performance of the three main components of the
system.We boil down the performance testing to the following three research questions:

\begin{itemize}
   \item RQ1: What is the overhead graph construction versus trace construction?
   \item RQ2: How does the performance of \textit{demands} compare when run using the graph or the execution trace?
   \item RQ3: How do the various implementations of \textit{demanded by}, the use of a trace, the direct graph implementation, or the dual of \opName{suffices}, compare in performance?
\end{itemize}

\subsubsection{RQ1: Overhead of Graph Construction Versus Traces}
We first proceed by comparing the time taken to evaluate a program in the
execution trace approach with the time taken to evaluate a program with the
dependence graph approach.
Since the graph is a more complex data structure to build compared to the trace,
we expect an increased overhead when evaluating a program and building the graph
compared to evaluating and building the trace.

In \tableref{eval-speedups}, we see that, as expected, the evaluation of programs
to their dynamic dependence graph does incur some increased overhead, ranging from
3 to 10 times slower than their trace based counterparts. \jb{Still subject to a
change}

We consider the primary focus of the evaluation to be in the types of interactions
that we can support, rather than the performance of the initial program evaluation.
This is because the evaluation only occurs once, and the overhead may disappear
over the course of several interactions.
We therefore consider the increase in evaluation overhead to be a worthwhile
tradeoff, when we consider the relative performance of implementing
\textit{demands} and \textit{demanded by}.

\subsubsection{RQ2: Demands Graphs Versus Traces}
We now compare the performance of the graphical and trace based implementations
when it comes to the computation of demands. We observe a significant increase
in the performance of demands using the graphical approach, shown in
\tableref{demands-speedups}.

This increased performance for computing \textit{demands} varies across the
examples, with some examples exhibiting a speedup of more than 50, and the lowest
-- the stateful dynamic time warp example -- closer to 12 times speedup.
This is still a significant improvement in performance across all of our tested
examples.

We attribute this performance improvement to the fact that the execution
trace approach requires the system to completely rewind the execution of the
original program, in effect evaluating it in reverse. We contrast this with the
current approach, which only needs to traverse the relevant part of the graph.

\subsubsection{Discussion}
We shall now consider the qualitative benefits and the performance results in
conjunction. The performance of evaluation is reduced due to the construction of
the graph being more complex than constructing an execution trace. We weigh that
against the relative ease of implementation, and the fact that evaluation now 
only needs to occur once. The performance gains in computing \textit{demands}
are significant. We argue that the user would only need to perform two or three
interactions with a program output in the graphical approach for the performance
gains to be realized. 

The performance change of \textit{demanded by} is less clear. Despite the fact
that the direct implementation uses the same underlying procedure as \textit{demands},
we do not see as consistent of a performance increase, and indeed in some cases
actually see a refression in performance. The implementation which uses the dual
of \textit{suffices} is somewhat more consistent, but with generall worse performance.
It remains to be seen exactly why this is the case, we conjecture that the structure
of the graph constructed during program evaluation significantly impacts the performance
of an implementation of \textit{demanded by}.

We overall consider our results to be positive, since we find a major performance
benefit in one part of the system, as well as an improvement in the simplicity of
the implementation itself. The mixed performance results of \textit{demanded by}
suggest further research is needed on how the structure of the graph affects the
system performance.
