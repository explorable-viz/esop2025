\section{Evaluation}
\label{sec:evaluation}

We shall now present a critical evaluation of our approach. Firstly we shall
consider the qualitative benefits of the approach in terms of conceptual
simplicity, and the relative ease of implementation. Secondly, we shall provide
an evaluation of our implementations performance compared to
an implementation of the prior state of the art in this field.

\subsection{Qualitative Evaluation Of Graphical Approach}
\todo{No Need to define backwards semantics}
A key benefit of our approach is in avoiding the need to define a backwards
evaluation function. In prior work in this area -- such as \citet{perera22} -- a
program produced an execution trace. To perform a backwards analysis such as
$\demandsR_D$, the developer was forced to implement a separate backwards evaluation
semantics using the execution trace until reaching the program inputs. This approach was laborious since
it can required the forwards and backwards evaluation functions to agree with
respect to the dependency analysis.

In contrast, by evaluating a program to a dynamic dependence graph
and deferring the specific dependency queries until the graph has been computed.
This allows us to use a simple procedure to
compute both $\demandsR_D$ and $\demandedByR_D$, whilst only requiring that the
developer implement the desired dynamic dependence graph once, in the forward
evaluation function, since the graph itself is what facilitates the two
directions of the approach.

\todo{Language Agnostic Approach}
The framework we have set up in this paper is language-agnostic. In \secref{conjugate},
we were able to give the core technical details of the approach without having to
mention the details of the language, or the specific choice of dependency relation.

We contrast this with the fact that alternate approaches do not compute and cache
the dependency structure -- as we do with the dependence graph -- but instead
the analyses are computed as part of evaluating a program, or un-evaluating an
execution trace. Thus, any changes to the dependency relation or to the language
itself need to be implemented multiple times. In contrast, with our approach
the developer only needs to implement the analysis once, and any changes to the
language or dependency relation used only require modification to a single
evaluation function.
\subsection{Benchmarking}

In order to test the performance of our dependency analyses, we implemented the
approach in the language described in \secref{core} in Purescript as a
language called \OurLang. Benchmarks were run on a commercial laptop, with an
Intel Core i7-10850H clocked at 2.70GHz and 16Gb of RAM. The benchmarks were run
on Google Chrome version 121.0.6167.160 and Javascript runtime V8 12.1.285.28.


In an interactive system, performance plays an enormous role in the experience
of a user. In order for evaluation to be a total success, we cannot allow
performance to degrade. It is possible that the dependence graph incurs a greater
overhead than the creation of an execution trace, as it is a more complex data
structure. Therefore, we need to compare the overhead of graph construction, and
trace construction. We also need to investigate the performance of \textit{demands}
and \textit{demanded by} between the implementation using a trace, and the one
using a dependence graph. We further need to consider the various implementations
of \textit{demanded by}, and determine if there is a clear performance difference.

We thus boil down the performance testing to the following three research questions:
\begin{itemize}
   \item RQ1: What is the overhead graph construction versus trace construction?
   \item RQ2: How does the performance of \textit{demands} compare when run using the graph or the execution trace?
   \item RQ3: How do the various implementations of \textit{demanded by}, the use of a trace, the direct graph implementation, or the dual of \opName{suffices}, compare in performance?
   \item RQ4: How does the performance vary in the size of the program input? \jb{not sure about this one}
\end{itemize}

\subsubsection{Choice of Examples}

We tested our system on a range of examples constituting the larger programs we
implemented in \OurLang. These programs represent a range of components a data
scientist may find useful in an exploratory data analysis scenario. Firstly,
we have implemented and tested performance on some matrix convolutions. Different
filter matrices create subtly different dependency structures, hence we have
implemented a few different filters. Secondly, we have an example of a more
sequential algorithmic program, an implementation of dynamic time warping,
known from time series analyis. Third, we have developed a prototype of a graphics
library, to demonstrate performance on bespoke visualization code. Finally,
we have tested some of the linked examples from \secref{overview}.

\subsubsection{RQ1: Overhead of Graph Construction Versus Traces}
We first proceed by comparing the time taken to evaluate a program in the
execution trace approach with the time taken to evaluate a program with with the
dependence graph approach.
Since the graph is a more complex data structure to build compared to the trace
we expect an increased overhead when evaluating a program and building the graph
compared to evaluating and building the trace.

In \tableref{eval-speedups}, we see that, as expected, the evaluation of programs
to their dynamic dependence graph does incur some increased overhead, ranging from
3 to 10 times slower than their trace based counterparts. \jb{Still subject to a
change}

We consider the primary focus of the evaluation to be in the types of interactions
that we can support, rather than the performance of the initial program evaluation.
We therefore consider the increase in evaluation overhead to be a worthwhile
tradeoff, when we consider the relative performance of implementing
\textit{demands} and \textit{demanded by}.

\subsubsection{RQ2: Demands Graphs Versus Traces}
We now compare the performance of the twin implementations when it comes to the
computation of demands. We observe a significant increase in the performance of
demands using the graphical approach, shown in \tableref{demands-speedups}. 

This increased performance for computing \textit{demands} varies across the
examples, with some examples exhibiting a speedup of more than 50, and the lowest
-- the stateful dynamic time warp example -- closer to 12 times speedup.
This is still a significant improvement in performance across all of our tested
examples.

We attribute this performance improvement due to the fact that the execution
trace approach requires the system to completely rewind the execution of the
original program, in effect evaluating it in reverse. We contrast this with the
graphical approach, which only needs to traverse the relevant part of the graph.
Thus in highly data-parallel examples -- like convolution -- we expect and indeed
observe a greater increase in performance. In contrast the graphics library code
and the dynamic time warp implementation do not exhibit quite the same level
of speedup, since they rely on a more sequential flow of data through the program,
which has the effect of forcing $\demandsR{}$ to traverse a greater portion of the graph.
