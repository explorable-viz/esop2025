\section{Evaluation}
\label{sec:evaluation}

We now compare the dependence graph approach presented in this paper with the main alternative style of
implementation, namely a bidirectional interpreter which produces an \emph{evaluation trace} during forward
evaluation, which is then used to implement backward evaluation~\cite{ricciotti17, psallidas18smoke,perera22}.
We start by considering the relative implementation effort required for the two approaches, and then provide
an experimental comparison of their performance.

\subsection{Qualitative Evaluation}

\todo{Rather than presenting this paragraph as an ``evaluation'', incorporate into the paragraph above as part
of the introduction to the performance evaluation.} For an implementator, the main benefit of the graph
approach is that it removes the need to implement a backwards analysis. The trace approach relies on a
bidirectional interpreter: a forward interpreter which which builds an \emph{evaluation trace} as well as a
result during forward evaluation, and then a backward interpreter that rewinds the trace to perform the
backwards analysis. Since the two directions of the interpreter need to be kept synchronised with respect to
the dependency analysis, updating the language requires modifying each direction in a manner that maintains
bidirectionality. In the graphical approach, the graph algorithms described in \figref{conjugate:algorithms}
for computing $\demandsR_{G}$ and $\demandedByR_{G}$ are language-agnostic and only have to be defined once.

\subsection{Experimental Evaluation}

To test the performance of our approach, we implemented our language from \secref{core} in PureScript. We used
our implementation to write a number of benchmarks that reflect realistic \todo{say we} targets of dependency
analyses \todo{meaning?} (\secref{evaluation:choice-of-examples}). PureScript is a natural implementation
language for this work as our focus on visualisations lends itself to building web-based interfaces
\todo{uh?}. Additionally, PureScript is the implementation language used by~\citet{perera22} in their
open-source implementation of the trace-based approach, thus enabling a more fair like-for-like comparison to
our work here \todo{hmm. why not just say we reimplemented/adapted their system?}. We then benchmarked the
implementations on an Intel Core i7-10850H 2.70GHz with 16Gb of RAM, using Google Chrome 121.0.6261.69 and
JavaScript runtime V8 12.2.281.16. We instrumented both systems in order to extract performance numbers.

In an interactive system, performance plays a critical role in a user's experience. We therefore compared the
performance of the graph-based and trace-based approaches by measuring the following:

\begin{itemize}
   \item Q1: Overhead of building a dependence graph versus building a trace
   \item Q2: Performance of graph-based \textit{demands} vs.~ performance of trace-based \textit{demands}
   \item Q3: Performance of various implementations of \textit{demanded by}: trace-based, graph-based using
   $\demandsAlg{}$, and graph-based using the dual of $\sufficesAlg{}$.
\end{itemize}

\noindent We assessed performance according to the guidelines proposed by \citet{nielsen93}:
\begin{itemize}
   \item 100ms: limit for an interaction feeling \emph{instantaneous}
   \item 1000ms: limit for a user's train of thought to remain uninterrupted, although
   they may perceive a delay
   \item 10000ms: limit to keep a user's attention on the system
\end{itemize}
We aimed for the interactive queries to stay as close as possible to the \emph{instantaneous} category
(captured by Q2 and Q3), and for the time taken to evaluate programs (corresponding to Q1) to be within the
limit for keeping a user's attention.

Overall, we observe a significant speedup in the performance of \textit{demands} using the graph approach,
from 33x speedup for the \textbf{stacked-bar-chart}, to more than 80x for \textbf{gaussian}. In particular,
every \textit{demands} query using the graph based approach is within the ``instantaneous'' category, whilst
all but two of the examples using the trace approach are in the ``noticable delay'' category. We attribute
this performance improvement to the fact that, in the trace approach, each query involves rewinding the entire
execution of the original program, in effect evaluating it in reverse, regardless of whether all of the trace
is relevant. In the graph approach, each query only traverses the relevant parts of the graph.

\subsubsection{Discussion of the results}
When comparing the performance of the graph and trace approaches, we observe that the only consistent
performance loss for the graph approach is due to the increased cost of evaluating a program to a graph versus
evaluating it to a trace (according to \textit{Q1}). We argue that this overhead is reasonable: the graph
only needs to be constructed once and does not impact subsequent interactions; and program evaluation time
does not exceed the limit for keeping the users attention on the system. Additionally, the fast response times
for \textit{demands} and \textit{demanded by} (according to Q2 and Q3), compared to the trace approach,
translate into quick responses to user queries. This is critical for the interactive exploration of digital
media.

Another notable aspect, which is observed for \textit{Q3}, is the performance of \textbf{G-DemBy-Suff}, which
takes the dual of the $\sufficesAlg{}$ algorithm. In the majority of cases, \textbf{G-DemBy-Suff} performs
significantly worse than \textbf{G-DemBy}; this seems most likely due to the fact that the ``complement''
subgraph traversed by the algorithm in this case is often much larger.
