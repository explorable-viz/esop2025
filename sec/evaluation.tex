\section{Evaluation}
\label{sec:evaluation}

We now present a critical evaluation of our approach. Firstly, we
consider the qualitative benefits of the approach in terms of conceptual
simplicity, and the relative ease of implementation. Secondly, we provide
an experimental comparison of the performance of our implementation and
that of the state of the art in the field.

\subsection{Qualitative Evaluation Of the Graphical Approach}
A key benefit of our approach is avoiding the need to define a backwards
evaluation function. In state of the art work in this area -- such as \citet{perera22} -- a
program produced an execution trace which was rewound in order to perform a backwards analysis such as
$\demandsR_D$. Consequently the developer had to implement a separate backwards evaluation
semantics using the execution trace, propagating a selection from the output backwards
until reaching the program inputs. This approach was laborious since
it required the forwards and backwards evaluation functions to agree with
respect to the dependency analysis.

Conversely, we evaluate a program to a dynamic dependence graph
and defer the specific dependency queries until the graph has been computed.
The developer needs to implement the desired dynamic dependence graph only once,
as part of their languages evaluation function. Then they can use a simple procedure to
compute both $\demandsR_D$ and $\demandedByR_D$ over this graph.

In \secref{conjugate}, we were able to give the underlying formalism without having to
mention any implementation details, or the specific choice of dependency relation.
Our ability to do so, combined with the prior remark regarding the need to implement
only a single construction of the graph contributes to ease of use. We suggest that the graphical approach
has the distinct advantage of being less sensitive to changes in the semantics
of the language. By removing the need for a pair of evaluation functions which
"agree", adding new constructs to a language is significantly easier, since the
only part of the language which is affected is the evaluation function which
the developer would already be forced to modify.


\subsection{Experimental Evaluation}
In order to test the performance of our approach, we implemented our language
from \secref{core} on top of Purescript, which we used to write a selection of
non-trivial examples that reflect realistic targets of dependency analyses
(\secref{evaluation:choice-of-examples}). We then benchmarked these programs on an
Intel Core i7-10850H 2.70GHz with 16Gb of RAM,
using Google Chrome 121.0.6261.69 and Javascript runtime V8 12.2.281.16. We
also implemented a variant of prior approaches that use execution traces, in
order to enable a like-for-like performance comparison.


In an interactive system, performance plays an enormous role in the experience
of a user. We have to test the performance of the three main components of the
system which we boil down to the following three research questions:

\begin{itemize}
   \item RQ1: What is the overhead graph construction versus trace construction?
   \item RQ2: How does the performance of \textit{demands} compare when run using the graph or the execution trace?
   \item RQ3: How do the various implementations of \textit{demanded by}, the use of a trace, the direct graph implementation using $\demandsAlg{}$, and the dual of $\sufficesAlg{}$, compare in performance?
\end{itemize}

\subsubsection{Choice of Examples}
\label{sec:evaluation:choice-of-examples}

We tested our system on a range of examples %constituting the larger programs we
implemented in \OurLang. These programs represent a range of components a data
scientist may find useful in an exploratory data analysis scenario. First,
we considered matrix convolution (\textbf{edgeDetect}, \textbf{emboss}, \textbf{gaussian}, 6 LoC each + 21 shared). Different
filter matrices create subtly different dependency structures, hence we 
implemented a few different filters. Second, we have an example of a more
sequential algorithmic program, namely an implementation of dynamic time warping,
known from the time series analyis (\textbf{compute-dtw}, 39 LoC). 
We provide a view of this program in \figref{dtw-source}.
Third, we developed a prototype of a graphics
library, to demonstrate the performance on bespoke visualization code (\textbf{grouped-bar-chart}, \textbf{line-chart}, \textbf{stacked-bar-chart}, 133 shared Loc).
Finally, we have tested some linked examples, 
particularly \figref{introduction:scatterplot} from \secref{overview} (\textbf{stacked-bar-scatter-plot}, 38 LoC)
and another linking example, (\textbf{bar-chart-line-chart}, 26 LoC).
Other than \textbf{compute-dtw}, we present the code for the rest of the benchmark
programs in \apdxsecref{evaluation-src-code}

Each benchmark is run 10 times. For each collection of benchmark runs,
we report the mean elapsed time, and the standard error of this sample.
Timing results are reported in milliseconds. When we refer to \textit{speedup}
or \textit{slowdown} with reference to a pair of implementations, we are
referring to the ratio of elapsed time on a given benchmark.

\subsubsection{RQ1: Overhead of Graph Construction Versus Traces}
We first proceed by comparing the time taken to evaluate a program in the
execution trace approach (\textbf{T-Eval}) with the time taken to evaluate a program with the
dependence graph approach (\textbf{G-Eval}).
Since the graph is a more complex data structure to build compared to the trace,
we expect an increased overhead when evaluating a program and building the graph
compared to evaluating and building the trace.

In \tableref{eval-SpdUps}, we see that, as expected, the evaluation of programs
to their dynamic dependence graph does incur some increased overhead, ranging from
3 to 14 times slower than their trace based counterparts. We report the ratio
of graph evaluation time to trace evaluation time in the third column (\textbf{Eval-Slowdown}).

\subsubsection{RQ2: Demands Graphs Versus Traces}
We now compare the performance of the graphical and trace based implementations
when it comes to the computation of \textit{demands}. We observe a significant increase
in the performance of \textit{demands} using the graphical approach, shown in
\tableref{demands-SpdUps}. We report time taken to compute \textit{demands}
with the trace and graph in \textbf{T-Demands} and \textbf{G-Demands}
respectively.

This increased performance for computing \textit{demands} varies across the
examples, with some examples -- most notably the two linked examples \textbf{bar-chart-line-chart} and
\textbf{stacked-bar-scatter-plot} -- exhibiting a speedup of more than 50, and the lowest
-- the stateful dynamic time warp example (\textbf{compute-dtw}) -- close to a 16 times speedup.
This is still a significant improvement in performance across all of our tested
examples.

We attribute this performance improvement to the fact that the execution
trace approach requires the system to completely rewind the execution of the
original program, in effect evaluating it in reverse. We contrast this with the
current approach, which only needs to traverse the relevant part of the graph.

\subsubsection{RQ3: Implementations of Demanded By}

We must finally investigate the performance of \textit{demanded by}. We must
compare the trace based approach with the graphical approach implemented by
using $\demandsAlg{}$, which we present in \tableref{equivalent-impls} as the
columns \textbf{T-DemBy} for the trace implementation, \textbf{G-DemBy-Dir}
for the graphical implementation using $\demandsAlg{}$, and comparing
relative performance in \textbf{Dir-SpdUp}.

We can also recover \textit{demanded by} from $\sufficesAlg{}$ by taking the
De Morgan Dual, which we also tested. This is presented in \textbf{G-DemBy-Suff}
and we compare its performance against the trace approach in \textbf{Suff-SpdUp}.

In all test cases apart from \textit{compute-dtw} we observe that at least one
of the two possible implementations in the graphical approach performs better
than the trace-based approach.

\subsubsection{Discussion}
The performance results of the system are mixed. Across each of the three performance
tests, we find that the results can vary quite wildly. First consider the
performance of evaluating a program to build its dynamic dependence graph. Whilst
we expected a loss of performance -- due to the inherently complicated task of
building the graph -- we see that this loss of performance can vary. Some of our
test programs exhibit a relatively small slowdown of 2.4 to 3 times slower than
trace based evaluation. On the other hand, some of the graphics programs exhibit
a dramatic loss in performance.

We see that generally, the performance of $\demandsR(\param)$ is much improved by
the graphical structure, but again there is a wide range of results for the amount
of speedup exhibited. The example \textbf{compute-dtw} shows the smallest degree
of performance improvement, but still averages out to 16 times faster than the
trace based approach. Some other examples -- notably the \textbf{gaussian} filter
convolution example, and the \textbf{line-chart} -- show a speedup of more than 70.

Finally we see an even wider range of performance results when we tested the three
implementations of $\demandedByR(\param)$. In the case of \textbf{compute-dtw}, we
observe a large loss of performance when using the direct implementation of 
$\demandedByR$, but the implementation which uses double complements and the
algorithm $\sufficesAlg{}$ takes approximately the same time as the trace approach.
On the other hand for every other test program the implementation using 
$\demandedByAlg{}$ is more performant. The speedup ranges from twice as fast in
the case of the convolutions to as much as a 100 times for \textbf{bar-chart-line-chart}. 
Using the dual of $\sufficesAlg{}$, we see that generally the performance is no
better than the trace based approach and in some cases -- notably \textbf{grouped-bar-chart}
-- is significantly worse.

The impact of the shape of the graph on the performance remains to be seen. The
convolution examples, \textbf{edgeDetect}, \textbf{emboss} and \textbf{gaussian}
involve a large number of parallel data dependencies. We would expect the parallel
dependencies to mean that $\demandsR(\param)$ and $\demandedByR(\param)$ exhibit
the greatest degree of performance improvement, since the algorithms would need
to traverse a relatively small portion of the graph. Despite this, we do not see
these examples showing a consistently higher degree of performance improvement
than the other cases. Similarly, we do not have a clear picture as to why some
examples -- \textbf{compute-dtw} --  perform poorly using the $\demandsAlg{}$
implementation of $\demandedByR(\param)$, and some perform poorly using the
$\sufficesAlg{}$ implementation. We shall touch on this in the discussion of
future work.

We overall consider our results to be positive, since we find consistent performance
benefit in one part of the system, as well as an improvement in the simplicity of
the implementation itself. In our view, the loss of performance in evaluation is
acceptable, since we generally find that the implementations of $\demandsR(\param)$
and $\demandedByR(\param)$ are significantly faster. Combined with the qualitative
benefits to the implementation itself, we believe that our implementation serves
as a viable demonstration of the approach.
