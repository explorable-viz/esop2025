\section{Evaluation}
\label{sec:evaluation}

We shall now present a critical evaluation of our approach. Firstly we shall
consider the qualitative benefits of the approach in terms of simplicity, and
eases the experience of someone implementing the dependency analysis. Secondly,
we shall provide some performance evaluation of our implementation compared to
an implementation of the state of the art approach in this field.

\subsection{Qualitative Evaluation Of Graphical Approach}
Benefits of graphical approach:
\begin{itemize}
   \item No need to define backwards semantics
   \item Language agnostic approach
   \item Separation of concerns
\end{itemize}
\todo{No Need to define backwards semantics}
A key benefit of our approach is in avoiding the need to define a backwards
evaluation scheme. In prior work in this area -- such as \citet{perera22} -- the
developer was forced to implement a separate backwards evaluation semantics, which
propagated selection information upwards through the execution trace until reaching
the program inputs. This approach was laborious. In contrast, whilst evaluating
a program to a dynamic dependence graph allowed us to use a simple procedure to
compute both $\demandR_D$ and $\demandByR_D$, whilst only requiring that the
developer implement the desired dynamic dependence graph. 
\todo{Language Agnostic Approach}
The framework we have set up in this paper is language-agnostic. In \secref{sec:conjugate},
we provide the core technical details of the approach without having to mention
the details of the language, or the specific choice of dependency relation.
\todo{Separation of concerns}
Continuing the previous point of discussion, the separation of concerns is also
a benefit. The dependency relation only needs to be implemented once, as part of
program evaluation, leading to a more modular system. If a languages evaluation
function is parameterised by the dependency relation, then it becomes possible
to work with a variety of dependency relations without forcing the developer to
entirely reimplement the forward and backward semantics of evaluation.
\subsection{Benchmarking}

In order to test the performance of our dependency analyses, we implemented the
approach in the language described in \secref{core} in Purescript as a 
language called \OurLang. Benchmarks were run on a commercial laptop, with an
Intel Core i7-10850H clocked at 2.70GHz and !6Gb of RAM. The benchmarks were run
on Google Chrome version 121.0.6167.160 and Javascript runtime V8 12.1.285.28.

We tested the performance of our implementation against the approach employed in
the state of the art in this area. Our benchmarks were designed to answer the
following three research questions:
\begin{itemize}
   \item RQ1: What is the overhead graph construction versus trace construction?
   \item RQ2: How does the performance of \textit{demands} compare when run using the graph or the execution trace?
   \item RQ3: How do the various implementations of \textit{demanded by}, the use of a trace, the direct graph implementation, or the dual of \opName{suffices}, compare in performance?
\end{itemize}

In light of the simplicity of the graphical approach, we consider performance
evaluation a success if our performance is at least competitive with the state
of the art. We expect the construction of a dependence graph to be somewhat more
expensive than constructing a trace, but that our dependency analyses to be more
efficient.
