\section{Evaluation}
\label{sec:evaluation}

We now present a critical evaluation of our approach. We start by
considering its qualitative advantage in terms of conceptual
simplicity and ease of implementation with respect to the state of the art in the field, \citet{perera22}. Then, we provide
an experimental comparison of the performance of our implementation and
that of \citet{perera22}.

\subsection{Qualitative Evaluation of Our Approach}

Here, we consider the relative implementation burden of the current graph approach compared to the trace approach in \citet{perera22}.
As explained below, we hypothesise that our approach is easier to implement and maintain compared to the trace approach. 

Firstly, a key benefit of the graph approach is avoiding the need to implement a backwards
evaluation function. By contrast, in \citet{perera22}, a
program produces an execution trace that is rewound in order to perform a backwards analysis such as
$\demandsR$. Consequently, the developer has to implement a separate backwards evaluation
semantics using the execution trace, which propagates a selected output backwards
to the program inputs. This approach is burdensome since
it requires the forwards and backwards evaluation functions to ``agree'' with
respect to the dependency analysis.
Conversely, in our approach, once the dependence graph has been computed, the same procedure
can be used to compute both $\demandsR$ and $\demandedByR$ over the graph.

Secondly, our approach is less sensitive to changes in the semantics
of the language than \citet{perera22}. By removing the need for a pair of evaluation functions which
"agree", adding new constructs to a language is significantly easier: the 
only part of the language that is affected is the evaluation function, which
the developer would anyway have to modify.

\subsection{Experimental Evaluation}
In order to test the performance of our approach, we implemented our language
from \secref{core} on top of Purescript, which we used to write a selection of
non-trivial examples that reflect realistic targets of dependency analyses
(\secref{evaluation:choice-of-examples}). We then benchmarked these programs on an
Intel Core i7-10850H 2.70GHz with 16Gb of RAM,
using Google Chrome 121.0.6261.69 and Javascript runtime V8 12.2.281.16. Furthermore,
in order to enable a performance comparison, we also implemented the approach in \citet{perera22}, which uses execution traces.
\cd{Do we have to say that we implemented this? Isn't it publicly available?}

In an interactive system, performance plays a critical role in a user's experience. Thus, we compare the performance of our graph based approach
with the trace based approach in \citet{perera22}, which boils down to the following three research questions:

\begin{itemize}
   \item RQ1: What is the overhead of the graph construction versus the trace construction?
   \item RQ2: How does the performance of graph based \textit{demands} compare against the performance of trace based \textit{demands}?
   \item RQ3: How does the performance of the various implementations of \textit{demanded by} (i.e. trace based, graph based using $\demandsAlg{}$, and graph based using the dual of $\sufficesAlg{}$) compare?
\end{itemize}

\subsubsection{RQ1: Overhead of graph construction vs. trace construction}
In \tableref{eval-SpdUps}, we compare the time taken to evaluate a program in the
graph approach (\textbf{G-Eval}) with the time taken to evaluate a program with the
trace approach (\textbf{T-Eval}). As previously explained,
the graph and trace are being build as part of the respective program evaluations.
Since the graph is a more complex data structure to build compared to the trace,
we expect an increased overhead when evaluating a program and building the graph
compared to evaluating and building the trace.

We see that, as expected, the evaluation of programs
to their dynamic dependence graph does incur an overhead, being from
3 to 14 times slower than their trace based counterparts. We report the ratio
of graph evaluation time to trace evaluation time in the third column (\textbf{Eval-Slowdown}).

\subsubsection{Discussion of the results}
When looking at the overall performance comparison for the graph approach and the trace approach (as illustrated by \textit{RQ1, RQ2} and \textit{RQ3}), 
the construction of the graph is the only one that takes consistently more than the construction of a trace.
We argue that this is reasonable given that the graph is only constructed once, at the beginning, 
and it doesn't impact the subsequent interaction between the user and the system. On the contrary, the fast response time of
\textit{demands} and \textit{demanded by} translates into quick responses to user queries,
which is critical for the interactive exploration of digital media.
