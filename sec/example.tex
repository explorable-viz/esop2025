Imagine you are an environmental data scientist, studying the relationship between
a nations economy and its environmental impact. \figref{energy-query} shows a program,
written in \OurLang, and its output, a bubblechart. The source file - \figref{energy-query-1} makes reference
to two variables, \textit{renewables} and \textit{non\_renewables}, which are defined
in two separate tables of data. Identifying the data from the two disparate
datasets that contribute to the structure of each bubble in the chart is non-trivial,
especially since each table is arranged differently.

Since the input data comes from two sources, we can lift a technique from
data visualization called \textit{brushing and linking} \citep{becker87}, in which
a selection made in one of the views of the data is propagated to the others.
Historically, this technique is implemented in an ad-hoc manner, for a given
visualization and the data it consumes. 

Recent work from \citet{perera22} provides a formal setting in which this task
can be expressed. In their work, a family of Galois connections can be constructed 
between inputs and outputs, allowing them to
identify the parts of a structured input which contribute to a structured output in
a fine-grained manner. Their work also allowed them to link multiple output views
of the same data together, as in \figref{linked-outputs-1}.

Dynamic program slicing in imperative languages has a rich history in the usage of
dependence graphs to track information flow through a program, representing control
flow statements and branches explicitly, as originally described in \citet{agrawal90}.

However, this work has some severe limitations, which we seek to address with our own work.
Firstly, whilst their work is aimed at interactive visualization of datasets, there is a
significant performance overhead when interacting with visualizations. Since they compute
their Galois connections via re-evaluating a program in the case of forwards slicing,
changing a selection on an input value takes the same amount of time as computing it
in the first place. To go in the backwards direction - selecting a structured output and
finding the inputs used to produce it - they must construct a trace at the same time as
evaluating the program, and then use this to propagate selection information backwards
through a fixed evaluation. For a system focussing on interactivity, this is a clear negative.

The second major issue with this prior work is that by factoring everything through evaluation
or backwards traversal of an execution trace, interpreting their slicing algorithms is
very difficult, and is inherently tied to their language. In particular, the idea of linking
structured outputs together naturally raises the question of using the Galois slicing framework
to try and link together multiple structured inputs which may \textit{co-operate} to produce
a particular output. The referenced work does not make it clear how one would approach this.

Our work, which aims to combine the dynamic dependence graph approach with the notion of Galois
connections has allowed us to give a simple description of the \textit{linked-inputs}
query described above, as a composition of two traversals of the same program graph.

In contrast to prior work which used traces the slicing procedures, and their duals, are
much easier to describe in the graphical setting. Backwards slicing -  as we shall discuss
in \secref{graph} - is effectively just a breadth-first search of a graph. Forward slicing
is not much more complicated. We shall also see how the graphical setting simplifies the De Morgan duals,
allowing us to construct the linked-inputs procedure via the composition of simple procedures
over the graph.

The benefit of this simplicity is that our slicing procedures are now far more efficient,
making interactive program slicing a tangible goal. Backwards slicing for example now takes
time linear in the size of the computed slice. The time complexity of forward slicing does not
admit such an easy description, but is empirically faster in most examples we have tested.

\figref{linked-inputs-1} shows a bubble chart aggregating data from two tables, as well
as a listing of the code used to produce it. Within the source listing, \textit{countries}
and \textit{cities} are variables which represent the two tables used to produce the chart.
The process of linking together inputs is sketched thusly: first the user selects the input data
they know they are interested in. Then \OurLang applies the forward slicing procedure on that
input selection, to select elements of the bubble chart the input data was used to compute.
Then we use the De Morgan dual of the backward slicing procedure to find the input
data in the second table which had a hand in creating the selected output.
