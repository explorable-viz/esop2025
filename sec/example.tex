One of the most ubiquitous yet challenging tasks in science is understanding the relationships
between the input and output variables of a problem. Communicating the results of a simulation
or the conclusion of some analysis can be made difficult by the inherent complexity of the problem
but also by the method in which it is communicated. When results are abstracted into
charts, information pertaining to how those charts were constructed - and from what data - is lost.
Figures can be difficult to interpret, even for a domain expert with access to the source code,
and instructions on recreating the results. This difficulty is further compounded
when the data is collated from multiple disparate sources, a widespread phenomenon
throughout the sciences. For example, in health research, meta-analyses such 
as \citet{NAKAMURA201929} are common, in statistics there are techniques like Bayesian model averaging
\citet{virdee_kaiser_ek_shuckburgh_kazlauskaite_2023}, and in computer science, join operations are 
employed in relational databases worldwide. \citet{selinger79}

As an example of this challenge, we begin with the scatter plot presented in \figref{energy-query-2}.
The axis labels tell us that the X-axis represents the proportion of energy capacity made up by
renewable sources, and the Y-axis represents the "capacity factor" of clean energy sources.
Alongside the caption, these provide us with a limited picture of what the chart represents.
But what does each circle in the plot represent, and how are their coordinates calculated? 
Without inspecting the program source in \figref{energy-query-1} we wouldn't see that
each circle represents a country. The source file also tells us how the axes were calculated, 
with the X-axis summing renewable electricity capacity, and dividing it by the
sum of the total electrity capacity. We can also see that the "capacity factor" on the Y-axis
represents the total generated power of clean resources, sum of each resources energy capacity.
We can also see that the data used is from the year 2018 and - a more subtle point -
that nuclear power may be considered a clean energy source, despite being non-renewable.
The source code still doesn't paint the whole picture however, we still don't know
which country each circle reprents. 

Our work takes the next step in improving the readability of such an example.
A user who is interested in improving their understanding of this sort of program
would likely begin by identifying some input data of interest. Either they are
only interested in this small portion of the input data, or are looking to build
their understanding by slowly increasing the amount of data they consider. 
In either case, once the user has identified the input data of interest, they will
want to proceed by selecting it. In \figref{related-inputs-main}, we label this
Step 1. Making a selection should be possible through a
simple interaction with some view of the table, like a mouse-click. 
Once a selection has been made, the elements of the chart which use the selected
parts of the input should be updated to make this relationship obvious to the user.
In this example, we demonstrate the circle has been selected by colouring it in.
This is represented in the figure by Step 2
Once the appropriate outputs have been identified, we consider
those outputs to now be selected. The third step is to identify the other inputs
that contributes to the selected output. In general it is likely that the input
data related to our initial selection will be distributed across varioustables,
including the one in which the initial selection was made. To avoid confusion
with data that the user has manually selected, we differentiate between \textit{primary}
and \textit{secondary} selections. A primary selection is one made by the user,
in our view of tables we represent these by highlighting the selected elements in green.
Any selection made by running our analysis is considered secondary, and highlighted in
gray. In \figref{related-inputs-main} these are labelled 3a and 3b.

Now that we have seen an example of the sorts of interaction our language supports,
we shall discuss the constituent parts which allow us to achieve it. A core goal
of this work is to allow for these interactive visualizations without placing an
increased overhead on the visualizations creator. We have therefore incorporated
the features needed to create these directly in a language, which we call \OurLang.
\OurLang is a functional programming language with records and datatypes, which bakes
in the analysis described above as part of program evaluation.

When a \OurLang program is evaluated, it does not only produce an output value
but also constructs a dependency graph $G$, similar to \citet{agrawal90}. In such a
graph, parts of structured values that arise in the programs execution are given
id's, and assigned to nodes. A directed edge exists from a node $n$ to a node $n'$
if, during execution, the value assigned to $n'$ was constructed by consuming part
of the value assigned to $n$, in a manner made precise later in the paper.

Once the graph $G$ has been constructed, we can begin to interact with it. Fix 
the set of nodes associated with inputs to be $\mathcal{A}$, and outputs to be
$\mathcal{B}$. We say that an output $b \in \mathcal{B}$ \textit{demands} an
input $a \in \mathcal{A}$ if there exists a path in $G$ from $b$ to $a$. We
can also say that $a$ is \textit{demanded by} $b$, if there is a path from $a$
to $b$ in the opposite graph, $G^{-1}$. Each of these is easily implemented by
simply finding the reachable nodes of a value in the appropriate graph.

In our example, the initial selected cell in the table is \textit{demanded by}
the highlighted circle in the output chart. We then find all of the other inputs
that the highlighted circle \textit{demands}, by finding its set of reachable
nodes, and intersecting those with $\mathcal{A}$. These nodes are those which
correspond to the cells of the tables which we have highlighted in gray.

It turns out that if we consider the inputs $x$ and outputs $y$ as part of some Boolean algebra,
then \textit{demands} and \textit{demanded by} are conjugate in the following sense:
$x \wedge demands(y) = \bot \iff demandedBy(x) \wedge y = \bot$.

In natural language, if $x$ is disjoint from the input data needed by $y$, then 
the output that uses $x$ is disjoint from $y$.

With these operators, we can define the analysis used to relate input data which co-operates
across two sources, by composing the two. We find outputs that demand $x$, then find out what
other inputs they demand. One could write \textit{rel(x) = demands(demandedBy(x))}. In \figref{linked-inputs-main}
we see a visual example of this, relating inputs from each of the two tables to the other.

The problem we have described are in some sense dual to another problem in data
visualization, the concept of \textit{brushing and linking} \citep{becker87}. 
This is the problem of identifying elements from multiple charts computed from
a common dataset. This historically has been implemented in an ad-hoc manner, for a given
collection of visualizations and the data it consumes. An example of this interaction
is given in \figref{linked-outputs-main}.

can express the problem of brushing and linking by inverting their composition:
$rel_{out}(y) = demandedBy(demands(y))$.

We are not the first to tackle this problem in a functional programming language.
The recent work of \citet{perera22} demonstrates a method to solve this problem by
constructing a family of Galois connections between the inputs and outputs of a given program.
In their work, a related outputs analysis makes use of a backwards slicing function, 
equivalent to our \textit{demands} operation, and the De Morgan Dual of their 
forwards slicing function, which is equivalent to our \textit{demanded by} function.
It is not necessarily surprising that our work can replicate their analysis, for the following reason.

It is well known that if you have a pair of conjugate functions,
then one of them will form a Galois connection with the dual of the other,
for example see \citet{MOLLER2006221}. This means that we can recapture the same,
whilst the Galois connection approach cannot easily capture the idea of related inputs.

One other important aspect where our work differs from this prior approach is in performance.
Our system works by realizing the dependency relations computed by our operations as a dynamic
dependence graph \citet{agrawal90}, computed during program evaluation. Then, as we shall
see later, we can characterize the procedures of computing related inputs or outputs as 
searching this graph and its opposite. This means only traversing relevant portions of
the computation, in stark contrast to the Galois slicing approach, which requires 
rewinding and replaying an entire program execution every time.

Since our focus is on making the interactions with visualizations both easy to interpret,
and easy to use, the performance improvements are highly valuable.
