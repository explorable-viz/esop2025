To see what built-in transparency might look like, consider the scatter plot in \figref{related-inputs-main}.
Various semantic questions about what is being represented in the chart arise immediately, some of which may
be partly answered by accompanying text. For example, the axis labels suggest that the x-axis represents some
kind of ratio (renewables to total energy capacity, perhaps), and that the y-axis represents the ``capacity
factor'' of clean energy sources. These give a sense of what the chart might be showing. But many unknowns
remain --- what the individual circles represent, which specific quantities are involved in the two ratios,
what energy types are being considered, which of those might count as ``renewable'', and so on. The fact that
these questions arise need not represent a problem with the visualisation per se. Indeed they are typical of
the questions that arise in any context where a reader is trying to understand the relationship between a
visualisation and the data being visualised.

Questions like these can in principle be answered by inspecting the source code for the visualisation
(\figref{energy-query}). Here line 14 suggests that x-axis values were computed by summing renewables capacity
and dividing by total capacity; line 15 shows that ``clean capacity factor'' on the y-axis is a ratio between
output and capacity for the sum of renewables and nuclear, suggesting that nuclear power, despite being
non-renewable, is being treated as a clean energy source. But deciphering this sort of information from the
source code involves finding the sources, downloading them, figuring out which parts are relevant, and then
trying to understand how those bits of code operate on the data set to produce particular aspects of the
visualisation. Moreover, all of this must take place outside of the ``comprehension context'' in which the
original question arose. Even a reader committed to a certain level of due diligence, such as a reviewer of a
scientific paper, may simply lack the time or know-how to do this.

In traditional media like hardcopy journals, this sort of opacity is unavoidable. By the time an article
reaches a reader, the trail of information relating data sources to charts or figures in the article is no
longer available. Skeuomorphic formats like Portable Document Format (PDF) that emulate paper fare no better,
but with a truly digital format --- perhaps an online paper or news article --- we should be able to do things
differently. Ideally we would like to enrich the artefact itself with interactions that allow the user to
query relationships between data sources and visualisations and other computed content \emph{in situ}.

To illustrate what this might look like in the scatter plot example, suppose the user identifies some input
data of interest, perhaps the bioenergy capacity of China for 2018. They move their mouse over the appropriate
cell in the table (\figref{related-inputs-main}, step 1) which is then highlighted in green. The system
responds by generating two further selections automatically. First, any elements of the scatter plot which
were computed using the selected input (\figref{related-inputs-main}, step 2) are given a similar green
highlight; in this case just one point is highlighted, and in fact only the $y$ coordinate of that point.
Then, the other inputs that contributed to that output feature (in other words, that were need to compute the
$y$ coordinate of that point) are highlight in grey (\figref{related-inputs-main}, 3a and 3b). (We use a
different colour to visually distinguish the \emph{answer} to the query from the inputs that initiated the
query in the first place.)

Whilst the this kind of ``data transparency'' result doesn't go the whole way to explaining how the
highlighted inputs were used to compute the highlighted output, it does move us substantially closer to the
visualisation alone being transparent, and entirely self-explanatory.

We would like these interactive queries to be provided automatically, rather
than implemented by the author of the visualisation on an ad-hoc basis.
Moreover we wish to provide some form of correctness and minimality guarantees
regarding query results.
These requirements suggested a solution built around dynamic program analysis,
specifically a dynamic dependence graph approach similar to \citet{agrawal90}
When a \OurLang program is evaluated, it does not only produce an output value
but also constructs a dependency graph $G = (V,E)$

In our graphs, parts of structured values that arise in the program's execution are given
ids which serve as the nodes $V$. A directed edge $(\alpha,\alpha') \in E$ is included
if, during execution, the value assigned to $\alpha'$ was constructed by consuming part
of the value assigned to $\alpha$, in a manner made precise later in the paper.

Once the graph $G$ has been constructed, we can begin to interact with it. Fix the set of nodes associated
with inputs to be $A$, and outputs to be $B$. We say that an output $b \in B$ \textit{demands} an input $a \in
A$ iff there exists a path in $G$ from $b$ to $a$. We can also say that $a$ is \textit{demanded by} $b$ iff
there is a path from $a$ to $b$ in the opposite graph $G^{-1}$ whichtrivially obtained from $G$ by reversing
the edges. Each of these operators is easily implemented by simply finding the nodes reachable from a given
start node in the appropriate graph.

In our example, the initial selected cell in the table is \textit{demanded by}
the highlighted circle in the output chart. We then find all of the other inputs
that the highlighted circle \textit{demands}, by finding its set of reachable
nodes, and intersecting those with $A$. These nodes are those which
correspond to the cells of the tables which we have highlighted in gray.

The idea of multiple inputs working together to produce some visual output is not
a unique problem. In fact, it is in a sense dual to a well known problem
in data visualisation. In data visualisation, it is common for the same collection
of input data to be reused across multiple charts, perhaps co-operating
with other input data. Multiple outputs making use of common input suggests the
problem of identifying elements in multiple charts which share their input data.
In the visualisation community the problem of selecting an element in a chart
and highlighting elements in other charts that use the same data is known as \textit{brushing and linking}
\citet{becker87}.

\todo{Historical context + introduction to the prior work}
Historically, solutions to the problem of brushing and linking have been ad-hoc
and relied on significant programmer effort in order to find the correct relation
between outputs. Adding a new visualisation would potentially require this
feature to be reimplemented or modified. In contrast, we can achieve the same
functionality without forcing the programmer to manually implement the linking.

As it happens, we are not the first to solve the problem of brushing and linking
in a functional programming language. Prior work from \citet{perera22} has
provided a solution through the user of Galois connections. The fact that our
work can recapture some of their results, whilst including a large amount of
extra functionality is not surprising, as we shall begin to make clear.

When considered as functions from sets of outputs to sets of inputs (resp:
sets of inputs to sets of outputs), then they satisify the property known as
\textit{conjugacy}, in the sense of \citet{jonsson51}:
$$
   A \cap \demands{B} = \emptyset \iff \demandBy{A} \cap B = \emptyset
$$

It is unsurprising that these two functions satisfy this property. Intuitively,
if the intersection of some inputs $A$, and the inputs that $B$ demands is empty,
then it is trivial that the set of outputs that $A$ is demanded by does not
contain any elements of $B$. This is equivalent to saying that the intersection
of the outputs that $A$ is demanded by with the set of outputs under consideration
$B$ is empty. \todo{This sentence needs to parse more niceley}

This property of conjugacy is what allows us to capture the functionality of the work
of Perara. In their work, a related outputs analysis makes use of a backwards slicing
function, equivalent to our \textit{demands} operation, and the De Morgan Dual of their
forwards slicing function, which is equivalent to our \textit{demanded by} function.

It is well known that if you have a pair of conjugate functions,
then one of them will form a Galois connection with the dual of the other,
for example see \citet{MOLLER2006221}. This correspondence is what allows us to
recapture their results. However, it is not so easy to adapt the Galois connection
approach to include related inputs queries.

One reason for this is the formulation of \textit{focussed} queries. Queries can
be made more precise by specifiying which parts of the output (or input) we want
to use to \textit{mediate} between our inputs (or outputs). In some cases, one
may find that an input is related to all other inputs due to some small component
of the output. We can therefore specify parts of the output which are uninteresting.
In effect the user is able to ask, for a selected input $x$, what are the other
inputs $X'$ that $x$ is related to, if we do not include relationships induced
by a specific output $y$. This allows us to make these queries more precise, with
the user able to adjust queries as they gain new information about a given
visualisation.
