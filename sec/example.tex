\subsection{Transparency by construction}

The transparency feature outlined above, which we call \emph{data transparency}, is ``extensional'': it says
what data is relevant, rather than revealing anything about why. In that sense data transparency falls short
of being a full explanation of how the input selection was used to compute the output selection. Nevertheless
it moves us substantially closer to research outputs self-contained enough to be able to reveal their
fine-grained relationships to data sources \emph{in situ}.

The key goal here is to enable data transparency automatically. One could attempt to implement similar
features on a bespoke basis for a given visualisation (see \citet{bremer15} for an elegant example); but not
only would that be difficult and error-prone, it would also require embedding knowledge of the dependencies
that arise in their visualisation code into that same program, making it fragile in the presence of changes to
that code. By putting this into a programming language instead, responsibility for correctness of the feature
lies with the implementors rather than users. These requirements suggested a solution built around dynamic
program analysis, specifically a dynamic dependence graph approach similar to \citet{agrawal90}

%

Once the graph $G$ has been constructed, we can begin to interact with it. Fix the set of nodes associated
with inputs to be $A$, and outputs to be $B$. We say that an output $b \in B$ \textit{demands} an input $a \in
A$ iff there exists a path in $G$ from $b$ to $a$. We can also say that $a$ is \textit{demanded by} $b$ iff
there is a path from $a$ to $b$ in the opposite graph $G^{-1}$ whichtrivially obtained from $G$ by reversing
the edges. Each of these operators is easily implemented by simply finding the nodes reachable from a given
start node in the appropriate graph.

In our example, the initial selected cell in the table is \textit{demanded by}
the highlighted circle in the output chart. We then find all of the other inputs
that the highlighted circle \textit{demands}, by finding its set of reachable
nodes, and intersecting those with $A$. These nodes are those which
correspond to the cells of the tables which we have highlighted in gray.

The idea of multiple inputs working together to produce some visual output is not
a unique problem. In fact, it is in a sense dual to a well known problem
in data visualisation. In data visualisation, it is common for the same collection
of input data to be reused across multiple charts, perhaps co-operating
with other input data. Multiple outputs making use of common input suggests the
problem of identifying elements in multiple charts which share their input data.
In the visualisation community the problem of selecting an element in a chart
and highlighting elements in other charts that use the same data is known as \textit{brushing and linking}
\citet{becker87}.

If we consider the notions of \textit{demands} and \textit{demanded by} as functions,
then we can see that computing the set of related inputs is equivalent to their
composition. It turns out that we can also solve the problem of brushing and linking
by simply inverting the composition of the two functions.

Consider the interaction shown in \figref{linked-outputs-main}. Similar to our solution to related inputs, we
begin by selecting an element of the chart, here we select a bar. Then, by applying the \textit{demands}
function, we find the data in the original table which is used to compute the height of the bar. Then we take
this data, and apply the \textit{demanded by} function. In this example, we find the points in the line chart
on the right hand side which make use of the input values selected by the application of \textit{demands}.

Historically, solutions to the problem of brushing and linking have been ad-hoc and relied on significant
programmer effort in order to find the correct relation between outputs. Adding a new visualisation would
potentially require this feature to be reimplemented or modified. In contrast, we can achieve the same
functionality without forcing the programmer to manually implement the linking.

As it happens, we are not the first to solve the problem of brushing and linking
in a functional programming language. Prior work from \citet{perera22} has
provided a solution through the user of Galois connections. The fact that our
work can recapture some of their results, whilst including a large amount of
extra functionality is not surprising, as we shall begin to make clear.

When considered as functions from sets of outputs to sets of inputs (resp:
sets of inputs to sets of outputs), then they satisify the property known as
\textit{conjugacy}, in the sense of \citet{jonsson51}:
$$
   A \cap \demands{B} = \emptyset \iff \demandBy{A} \cap B = \emptyset
$$

It is unsurprising that these two functions satisfy this property. Intuitively,
if the intersection of some inputs $A$, and the inputs that $B$ demands is empty,
then it is trivial that the set of outputs that $A$ is demanded by does not
contain any elements of $B$. This is equivalent to saying that the intersection
of the outputs that $A$ is demanded by with the set of outputs under consideration
$B$ is empty.

It is well known that if you have a pair of conjugate functions, then one of them will form a Galois
connection with the dual of the other, for example see \citet{moller06}. This correspondence is what allows us
to recapture their results. However, it is not so easy to adapt the Galois connection approach to include
related inputs queries.

\subsection{Focused queries}

With any dependency analysis, there are situations where a given output depends on many inputs, such as when
computing aggregates such as sums or averages. A challenge is then how to obtain informative queries in the
presence of such noisy dependency information. A variety of techniques may be helpful here, but for this paper
we consider how related inputs queries can be made more precise by specifiying which \emph{parts} of the
output we want to use to mediate between the inputs. By projecting away a problematic output (i.e.~one which
causes an input to be related to many other inputs), we can can obtain a \emph{query context} within which we
can ask more fine-grained queries of the form ``With respect to these particular outputs, what other inputs are
related to this input?''

The dual problem arises with related outputs, when an given output is related to many other outputs in virtue
of there being some inputs which are shared by all of them (perhaps a common constant, for example). Again by
restricting the mediating inputs to exclude the problematic input, we can obtain a query context within which
we can proceed to ask more fine-grained related outputs queries, of the form ``With respect to these particular inputs, what other outputs are related to this output?''
