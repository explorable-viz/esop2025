\subsection{Overhead}

In both the trace-based and graphical approaches, we construct an auxiliary data
structure during evaluation. In the trace-based approach, we construct what is
in essence a simplified version of the AST of the program, only representing
things such as the branch of a pattern match or conditional expression which
was taken. 

In contrast, the graphical evaluation approach works by annotating values with
vertices, and building sets of neighbors. We collect the sets of vertices and
edges produced at the end of evaluation, and only afterward construct the actual
representation of the graph. 

We can see in Table \ref{table:eval-speedups} that across our test-cases, trace
based evaluation takes about $54\%$ of the time that graph evaluation takes. We
believe that this is an acceptable level of performance loss, given the gains we 
make in slicing performance, which we discuss next.

\subsection{Slicing Performance}
The main benefit of representing the program's dependence structure on a graph
is the improvements to the speed of program slicing. We have already established
in Section \ref{sec:graph} that slicing in the graphical setting is much simplified
algorithmically. Since we are targeting interactive systems, we therefore feel
the gain in slicing speed is worth the loss of performance in evaluation.

Our metric for the improvement to slicing speed is based on a well-known set of
criteria proposed in \cite{Nielsen93}, which we paraphrase here:

\begin{itemize}
    \item \textbf{0.1 seconds} or less feels instantaneous to the user
    \item \textbf{1.0 seconds} is the limit before the users flow of thought feels
    interrupted
    \item \textbf{10.0 seconds} is the limit for keeping the users attention. Anything longer
    than this and the user will shift their focus to other tasks
\end{itemize}

\subsection{Old}

The practical motivation for representing dependency structures as a graph, informally,
is that computing a slice is much more performant in the graphical setting.
As we have established, backwards slicing is equivalent to computing the set of
reachable nodes from a given selection, a procedure which runs in linear time with
respect to the size of the reachable set. As a result, we shall see that performance
of slicing is improved by several orders of magnitude. We shall see that
construction of the graph does however introduce a fairly significant performance
overhead in contrast to constructing a sequential trace, however this cost vanishes when
one computes multiple slicing queries over a single computation.

We shall see that our graphical implementation pushes slicing queries into the bracket of
instantaneous user feedback. In terms of designing interactive systems, we argue that the
increased cost in constructing the dependency graph is well worth it, given that it
facilitates such a stark increase in performance of slicing queries.

\subsection{Testing Methodology}
We describe here the specifics of each individual benchmark, before moving on to
a discussion of the results. For performance measurements of the trace-based
approach, we summarize evaluation time, and the times taken for forward and 
backward slicing, as \textbf{Trace-Eval},\textbf{Trace-Fwd}, and \textbf{Trace-Bwd}.
    
For benchmarking the graphical system, we must be careful to define the individual
performance tests. For a given test-case, we first run - and time - evaluating
to a graph in \textbf{Graph-Eval}. This fixes the dependence graph $G:\mathcal{A} \to \mathcal{B}$,
where $\mathcal{B}$ denotes a distinguished set of output vertices, and $\mathcal{A}$
a distinguished set of inputs. We can then define the individual benchmarks in
terms of the operators we defined in \ref{sec:graph}. Since the operators we
defined in the prior section have multiple equivalent definitions, we take care
to delineate between the operator, and the implementation of that operator we are testing.

\textbf{Graph-Bwd} refers to running the backward slicing procedure over a fixed
selection. We use this to compute a relevant input selection as we have described.
The input selection we compute during \textbf{Graph-Bwd} is the selection we then
feed into the forward slicing procedure which we time as part of \textbf{Graph-Fwd}.
This is also where we validate round-tripping, albeit this is not relevant to the 
discussion of performance.

\subsection{Backward Slicing}
Despite the increased overhead in constructing the dynamic dependence graph for
a given execution, we see a dramatic reduction in the time it takes to perform
backward slicing on a graph. In the examples presented in Table \ref{expensive-bwd}
we observe backward slicing takes much less than 0.1 seconds, putting the system
firmly in the instantaneous bracket under Nielsens guidelines.
For large systems with complex and opaque data dependency structures, this is
a clear benefit as we can see that after performing two backward slicing
queries, the overall time taken is less in the graphical setting. It is also
unlikely that users will want to run a computation and then only be interested
in a single slicing query.

Finally, from a usability perspective, it is more important to have the interactive
component of the system be highly performant. Developers often have to contend
with evaluation or computation time anyway, and we prefer the cost be
incurred up front, rather than repeatedly.

\subsection{Inefficient Forward Slicing}
As we mentioned earlier in \ref{sec:graph}, we can theoretically get by without
providing an explicit definition of forward slicing. Instead, we can derive the
forward slicing procedure in terms of backwards using the De Morgan dual on the
opposite graph. 

In practise however we see a significant reduction in performance when performing
forward slicing in this manner. For some extreme examples, consider the right-most
column of Table \ref{expensive-fwd}. We see that in the pictured test cases,
performance of forward slicing as the De Morgan dual of backwards is particulary poor.

the complementation of a selection, which in a very large graph can be expensive. 

\subsection{Discussion}
We can see that whilst the graphical slicing paradigm can improve the performance
of program slicing dramatically, the increase in performance is varied. It 
initially appeared that speedup in slicing time was inherently tied to the
size of the dynamic dependence graph and equivalent trace, but this is not true.

Instead the computational speedup is more closely tied to the structural 
properties of the program of interest, and it's resultant dependence graph
We have tested on several non-toy programs, and we note that there is a 
high variance in speedup of both forward and backward slicing time. We see that
some examples - such as Dynamic Time Warping - experience approximately an
eighttimes performance increase in both forward and backward slicing, whereas
our convolution examples demonstrate speed increases on the order of 100s.

The reason for this disparity is the inherent data-parallelism of certain
computations. A single iteration of a convolution creates very "local" dependency
structure. A cell in the top left of the output matrix only depends on a small
section of the input image. We therefore expect that the graph produced
in evaluation has lots of inputs which do not cooperate.

In contrast, the Dynamic Time Warping algorithms output matching 
requires traversing the entire cost matrix computed in evaluation, and a cell in
the cost matrix relies on the computation of it's left, upward, and diagonal
neighbors. The implication of this is that the data depdendency through the
the computation is in a sense more sequential than that of, for example
convolution.
