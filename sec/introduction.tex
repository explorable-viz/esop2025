\section{Introduction: Towards Transparent Research Outputs}
\label{sec:introduction}

Whether formulating national policy or making day-to-day decisions about our own lives, we increasingly rely
on the charts, figures and text created by scientists and journalists. Interpreting these visual and textual
summaries is essential to making informed decisions. However, most of the artefacts we encounter are
\emph{opaque}: they are unable to reveal anything about how they relate to the data they were derived from.
Whilst one could in principle try to use the source code and data sources to reverse engineer some of these
relationships, this requires substantial expertise, as well as valuable time spent away from the
``comprehension context'' in which we encountered the output in question.  These difficulties are only
compounded when the information presented draws on multiple data sources, such as medical
meta-analyses~\citep{dersimonian86}, ensemble models in climate science~\citep{murphy04}, or queries that span
multiple database tables~\citep{selinger79}. Even professional reviewers may lack the resources or inclination
to embark on such an activity. Perhaps more often than we would like, we end up taking things on trust.

With traditional print media, a ``disconnect'' between outputs and underlying data is unavoidable. For digital
media, other options are open to us. One way to improve things is to engineer visual artefacts to be more
``self-explanatory'' so they can reveal the relationship to the underlying data to an interested user.
Consider the histogram in \figref{introduction:bremer} showing urban population growth in Asia over a 10-year
period \cite{bremer15}. There are many questions a reader might have about what this chart represents --- in
other words, how visual elements map to underlying data. Do the points represent individual cities? What does
the colour scheme indicate? Which of the points represent large cities or small cities? Legends and other
accompanying text can help, but some ambiguities inevitably remain. The entire value proposition of a summary
after all is that it presents the big picture at the expense of certain detail.

\citeauthor{bremer15} approach was to implement an interactive feature that allows a user to explore some of
these provenance-related questions \emph{in situ}, i.e.~directly from the chart. By selecting an individual
point, they are able to bring up a view showing the data that point was calculated from. In the figure the
highlighted point represents data for Chiang Mai and the plotted value of 10.9\% was derived from an increase
in population density from 4,416 to 5,010 people per sq.~km. Features like these are valuable as comprehension
aids, but are laborious to implement by hand and require the author to anticipate the queries a user might
have. For these reasons they also tend not to generalise: for example \citeauthor{bremer15}'s visualisation
only allows the user to select one point at a time.

\subsection{Data transparency as PL infrastructure}
\label{sec:introduction:data-transparency}

An alternative approach is to treat data provenance features like these as a language infrastructure problem,
baking lineage or provenance metadata directly into outputs so that interactive queries of this sort can be
supported automatically~\cite{psallidas18,psallidas18smoke,perera22} \todo{Reinstate Psallidas discussion
here, and more general point about relationship between interaction and data selection.} The burden of
implementing these features no longer falls on the author of the content, who can concentrate purely on data
visualisation, and the consumer of the content can formulate any query supported by the infrastructure. In
contrast to \citet{bremer15} \todo{revisit}, the relationship to data is incrementally discoverable, revealed
as the user interacts with the parts of the output they care about, ideally with some kind of formal guarantee
that the revealed data is in some sense ``minimal and sufficient''.

We follow the direction of~\citet{ricciotti17} and \citet{perera22}, and propose a new bidirectional program
analysis framework which supports such fine-grained \emph{in situ} provenance queries, which we call
\emph{data transparency}. We will use \figref{introduction:related-inputs} to illustrate this concept. The
figure presents a data visualisation which investigates the efficiency of clean energy usage, broken down
geographically. The data is split across two tables providing information about \textit{renewable} and
\textit{non-renewable} energy sources; some of the data from the tables has been summarised in the scatter
plot on the right, where the x-axis represents the total renewables capacity over total energy capacity, and
the y-axis denotes the clean capacity factor computed as the total clean energy output over the total clean
energy capacity. There are four scenarios that are constitutive of data transparency as we envisage it here;
we now discuss these in some detail.

\paragraph{Fine-grained linking of the data to the view}
A user may also be interested in following the link between the input data and the output view. For instance,
the user may select China's bioenergy capacity (highlighted in green in~\figref{introduction:related-inputs},
row 205 in the data on the figure's left). Then, our system, through an operator we write as
$\demandedByR_{G}$, traces the data contained in this cell to the parts of the plot it was used to compute
(the green point in the plot). The bioenergy capacity contributes to both components of the point, namely the
total renewables capacity over total energy capacity and the clean capacity factor. We read $\demandedByR_{G}$
as computing ``what outputs is some input data \emph{demanded by}?''.

compute the point in the plot (all data highlighted in grey in the tables). \todo{Probably unwise to use a

\subsection{Contributions}
\label{sec:introduction:contributions}

We introduce a new bidirectional program analysis framework for a general-purpose programming language which
supports interactive exploration of fine-grained I/O relationships. We make use of dynamic dependence
graphs~\cite{ferrante87, agrawal90}; this enables our approach to be language-independent, separating queries
over dependence graphs from the problem of deriving the dependence graph for a particular program. Our
specific contributions are as follows \todo{do we really need three citations of \cite{perera22} here?}:

\begin{itemize}

\item A new formal framework for bidirectional provenance queries over dependence graphs, formalising the
$\demandsR_{G}$ and $\demandedByR_{G}$ operators introduced informally in \secref{introduction:data-transparency},
which we show to be \emph{conjugate} in the sense of~\citet{jonsson51}. We relate our framework to
bidirectional analyses based on Galois connections (e.g.~\citet{ricciotti17,perera22}).

\item A novel \emph{linked inputs} analysis, a relation of mutual relevance or “cognacy” which arises between
inputs when they contribute to common features of the output. The design of our framework makes it
straightforward to implement this analysis by composing $\demandsR_{G}$ and $\demandedByR_{G}$. We also show
how a dual \emph{linked outputs} analysis, available in prior work \cite{perera22}, is easily obtained by
transposing the two operators.

\item Improved performance with respect to \emph{trace-based} approaches~\cite{perera22}, one of the
predominant techniques for achieving bidirectional program analysis. Using usability metrics from
\citet{nielsen93}, we find that $81\%$ of the queries we tested over larger examples execute at a speed that
appears instantaneous to a user, compared to $25\%$ using an implementation based on traces. Fast response
time is particularly important for the interactive data visualisations we~target.

\end{itemize}

\paragraph{Roadmap} The paper is organised as follows:

\begin{itemize}[leftmargin=*]
\item \secref{conjugate} defines a new program analysis framework over dynamic dependence graphs, introducing
  the cognacy operator $\relInputR_G$ (``linked inputs'') and unpacking the intuitive relationship between its
  two components $\demandsR_{G}$ (``demands'') and $\demandedByR_{G}$ (``demanded by'') in terms of
  \citeauthor{jonsson51}'s notion of conjugate operators over Boolean algebras. We also introduce the dual
  cognacy operator $\relOutputR_G$ (``linked outputs'') and explain the relationship to Galois connections: $f$
  and $g$ being conjugate is equivalent to $f$ and the De Morgan dual of $g$ forming a Galois connection. We
  give procedures for computing $\demandsR_{G}$ and $\demandedByR_{G}$.
\item \secref{core} defines a core functional language with an operational semantics that pairs every result
  with a dynamic dependence graph suitable for computing $\demandsR_{G}$ and $\demandedByR_{G}$. We show how to represent
  (parts of) values as vertices in the graph. We also show how our operators can follow information back to environments,
  with projections.
\item \secref{evaluation} evaluates our implementation based on graphs and conjugates against one based on
 traces and Galois connections. We contrast the implementation burden of the two approaches, and the
 performance  of building trace vs.~building dependence graphs and computing $\demandsR_{G}$ and
 $\demandedByR_{G}$ over~each.
\item \secref{related-work} reviews related work in more detail, including program slicing and dynamic dependence~graphs.
\item \secref{conclusion} wraps up with a discussion of some limitations. In particular, the sort of transparency
infrastructure proposed in this paper is purely extensional and falls short of providing full explanations of
how output parts are related to input parts. We discuss extending this to more ``intensional'' forms
transparency and propose some other ways in which the present system could be improved.

\end{itemize}

\noindent
We implement our approach in a pure functional programming language called \OurLang. The author of a \OurLang
visualisation expresses their chart as a pure function of the inputs, using a set of built-in data types for
common visualisations; a d3.js front end automatically enriches the rendered outputs with support for visual
selection and the data transparency queries shown in
\figrefTwo{introduction:related-inputs}{introduction:scatterplot}. Our implementation is open source and
available online (given later in a deanonymised version). We also provide an anonymised web demo at
\href{http://opencomputation.org/}{\textsf{http://opencomputation.org/}}.
