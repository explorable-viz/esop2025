\subsection{Dynamic Dependence Graphs}

Dynamic dependence graphs have been used previously in functional languages to implement incremental
evaluation~\cite{acar02, acar06b}. In contrast to their work, which focuses on efficiently propagating changes
for inputs to computations, we are concerned with the implementation of interactive data exploration systems.
\JBnote{With respect to program slicing, \citet{field98} use dynamic dependence graphs on a subset of Pascal. In 
their work, the authors demonstrate the application of dynamic dependence graphs to in languages implemented as
term-rewriting systems, showing how this can be used to construct elaborate error reporting for things like type
errors. Internally, their dependence graphs represent a complete account of the reduction steps in a programs 
execution -- as a term graph -- as opposed to our dependence graphs which only represent value-to-value
dependencies. Our work is also distinct in that, by focussing on allowing the user to explore dependencies 
in interactive visualisations, we assume that the program has already executed, rather than using the information
for static error checking.}

More recently there has been a body of work aimed at using dynamic dependence graphs to assist in program
fault localisation, but again these are not focused on interactive visualisation systems, but rather on bug
finding in programs. For a survey see \citet{Soremekun2021} \todo{focus on the difference in the information
the graphs contain, rather than how they are used?}.

\todo{Other provenance approaches}

\cite{dietrich22} attempts to simultaneously explain both value and control dependencies in recursive database
queries and user-defined functions. Their work takes an SQL query and rewrites it into a pair of queries which
compute not only the output table, but the provenance of the values it contains. In order to modify our
approach to work in this setting, we would need to encode extra information into the edges of the graph,
specifically whether an edge is a control-flow edge -- coming from an if-else or a pattern match -- or a value
edge -- from producing a new value out of old ones. This information roughly corresponds to the ``why'' and
``where'' provenance described in the database setting. Further we would need to use a dependency relation
which agrees with the semantics of an SQL query or user-defined functions, since a relational database is
semantically distinct from our functional setting.

\subsection{Galois Slicing}

\todo{This section feels long and overlaps a bit with earlier discussions about advantage of dependence graphs
over traces.} Galois connections between lattices offer an appealing mathematical foundation for bidirectional
dynamic program analysis, cleanly characterising input-output relationships in terms of demand and sufficiency
\cite{perera12a,perera16d,ricciotti17}. In these works, Galois connections are applied to the problem of
program slicing. The upper adjoint -- which characterises forward slicing from inputs to outputs -- can be
thought of as a \emph{sufficiency} operator, picking out all the outputs which can be computed using only a
particular set of inputs; the lower adjoint, which characterises backward slicing, is a \emph{demand}
operator, picking out the specific inputs needed to compute a particular set of outputs. \citet{perera22}
extended this approach to a setting where slices have complements and the slices of a particular program or
value form a Boolean lattice; they then showed how the De Morgan dual of the upper adjoint can be used to pick
out \emph{linked outputs}, namely the other outputs that ``compete'' with a given set of outputs in the sense
of demanding some of the same inputs, and proposed this as a framework for understanding the ``brushing and
linking'' feature commonly used in data visualisation.

However, implementations of Galois slicing efficient enough to support the kind of interactive applications
considered here have proved elusive. To compute the two analyses, implementations have relied on a sequential
execution record, usually taking the form of a big-step or small-step trace. The forward analysis uses the
trace to ``replay'' the computation, propagating information about resource availability from inputs to
outputs; the backwards analysis uses the trace to ``rewind'' the computation, propagating information about
demand from outputs to inputs. This overly sequential approach makes the approach unable to exploit the very
independence that makes slicing useful in the first place. Moreover, the backwards analysis makes frequent use
of lattice join ($\join$) to combine slicing information computed along different branches of the computation
\todo{mention this earlier when we're conjecturing why graph approach is faster}. Joining closure slices in
particular becomes expensive because of the contained environments (which in turn contain closures), and these
issues have made the approach prohibitively slow for interactive use. Compared to Galois slicing, our approach
of decomposing the problem into a graph semantics and a pair of analyses over the graph significantly reduces
the implementation burden on the developer, since the algorithms for the program analyses are
language-agnostic and thus only need to be implemented~once.

\subsection{Linked Visualisation}

In data visualisation it has long been recognised that when users interact with visual elements by clicking or
lassoing, the intention is typically to manipulate the underlying data. This has lead to various techniques
for inverting selections in visual space to obtain selections in the input data~\cite{north00, heer08}.

We are not the first to consider shifting the burden of interactive visualisations into the language runtime.
Reactive Vega~\cite{satyanarayan17} presents a system for building interactivity in visualisations. Vega is a
declarative DSL for constructing interactions with visualisations. The features of Vega allow for more
complicated interactions than our own work at present, however these are hampered by requiring the designer to
learn multiple separate languages \todo{spurious}. Further, the syntax of Vega for combining these
interactions is non-obvious to a new user \todo{also spurious}. In contrast, whilst our work provides a
smaller set of interaction primitives \todo{we don't provide primitives that the programmer can use -- in that
sense we don't support ``interactivity'' at all, rather interactivity is a built-in, but limited, featured} it
frees up the developer to focus on building their data analysis programs, leaving the burden of implementing
selections to the language itself. The benefit of including everything into the base language is that it
reduces the number of tools that a developer needs proficiency with \todo{spurious, see above}. Our linking of
visualisations is similar in spirit to the work of \citet{north00}. In that work, the authors design a modular
system for replacing visualisations of databases. Their system is modelled by relational database schema, and
is designed to facilitate interactions with these modular visualisations, but is limited to data from
relational databases, whereas ours can be applied to data of any shape, as long as it is supported by our
language. Devise \citep{livny97} is another visualisation framework for building interactive visualisations of
relational database tables. Similar to \citet{north00}, their work is defined by its usage of relational
databases, and the way they create a semantics for queries on visualisations using the model of relational
database queries.

\subsection{Transparent research outputs}

\citet{dragicevic19} also develop techniques for transparent research outputs, via explorable multiverse
analysis, exposing \emph{analysis parameters}, the methodological choices made in designing a data analysis.
Since different choices made in design will impact the conclusions of the analysis, they exposes the choices
made to users, and allows them to toggle between possible choices at given points in the analysis, observing
how they impact the results. We view our work as complementary to theirs, since we are more concerned with the
dependencies observed within a specific choice of analysis parameters, rather than the choices themselves.
Toggling choices in their interactive artifacts updates the artifact globally, and it can be different to know
the exact impact that one of these analysis parameters has on results. It seems reasonable to package our
dependency analysis alongside such a multiverse analysis, allowing the user to observe the dependencies on a
methodological choice, as well as the underlying data dependencies used in the analysis.
