\section{Related work}
\label{sec:related-work}

\subsection{Data Provenance}

There is a long history of provenance techniques, ranging from coarse-grained (document-level) provenance tracking [...] to fine-grained database provenance [...]. In terms of fine-grained techniques for structured outputs like visualisations, the two main areas of prior work are [psallidas] for query languages, and [perera] for general-purpose languages.

\cite{dietrich22} attempts to simultaneously explain both value and control dependencies in recursive database
queries and user-defined functions. Their work takes SQL queries, and rewrites them into a pairs of queries
which compute not only the output table, but the provenance of the values it contains.

\JBnote{In \cite{fehrenbach19}, the authors present a system for language-integrated data provenance
for the LINKS programming language \cite{cooper06}. Their system is rooted in the nested relational calculus (NRC)~\cite{BUNEMAN19953},
and -- despite integration with a general purpose language -- only supports provenance queries for an
embedded SQL-like language, rather than dependency queries over the more general constructs in LINKS.
Extending our work to support similar provenance queries would require revisiting the dependency relation,
since we do not distinguish between control-flow -- coming from an if-else or a pattern match -- and value
dependencies -- from producing new values out of old ones. This information roughly corresponds to the ``why'' and
``where'' provenance described in the database setting. We would also need to consider how SQL queries and the
NRC differ semantically from our core functional calculus.}

\subsection{Dynamic Dependence Graphs}

Dynamic dependence graphs have been used previously in functional languages to implement incremental
evaluation~\cite{acar02, acar06b}. In contrast to their work, which focuses on efficiently propagating changes
for inputs to computations, we are concerned with the implementation of interactive data exploration systems.
\JBnote{With respect to program slicing, \citet{field98} use dynamic dependence graphs on a subset of Pascal. In
their work, the authors demonstrate the application of dynamic dependence graphs to in languages implemented as
term-rewriting systems, showing how this can be used to construct elaborate error reporting for things like type
errors. Internally, their dependence graphs represent a complete account of the reduction steps in a programs
execution -- as a term graph -- as opposed to our dependence graphs which only represent value-to-value
dependencies. Our work is also distinct in that, by focussing on allowing the user to explore dependencies
in interactive visualisations, we assume that the program has already executed, rather than using the information
for static error checking.}

More recently there has been a body of work aimed at using dynamic dependence graphs to assist in program
fault localisation. \JBnote{Generally, work that uses dependence graphs for this purpose are
defined for imperative languages, identifying \emph{statements} which depend on each other. Our languages
encodes much of its control flow via pattern matching on data. We can therefore encode much of the
same information simply by considering data dependencies.}
For a survey on other techniques, see \citet{Soremekun2021}.

\subsection{Galois Slicing}

Although we do not consider program slices in the present work, our approach is closely related to program
slicing techniques based on Galois connections \cite{perera12a,perera16d,ricciotti17}. In these works, which
use a bidirectional interpreter, the forward and backward directions of the interpreter correspond to our
\emph{sufficiency} ($\sufficesR$) and \emph{demands} ($\demandsR$) queries. \citet{perera22} extended this
approach to a setting where slices have complements, and showed how composing the backward analysis with the
De Morgan dual of the forward can be used to implement the ``brushing and linking'' feature commonly used in
data visualisation. As well as requiring a bidirectional interpreter, the main difficulty with this approach
has been achieving interactive performance. To provide the bidirectional interpreter, implementations have
relied on a sequential execution trace, used in the forwards direction to ``replay'' the computation,
propagating sufficiency information from inputs to outputs, and in the backwards direction to ``rewind'' the
computation, propagating demand from outputs to inputs. As discussed in \secref{evaluation}, and in contrast
to the graph approach presented here, this sequential approach is unable to exploit the very independence that
makes slicing useful in the first place.

\subsection{Linked Visualisation}

In data visualisation it has long been recognised that when users interact with visual elements by clicking or
lassoing, the intention is typically to manipulate the underlying data. This has lead to various techniques
for inverting selections in visual space to obtain selections in the input data~\cite{north00, heer08}.

\JBnote{Ours is not the first work to shift the burden of interactive visualisations into the language runtime.
Reactive Vega~\cite{satyanarayan17} presents a system for declaratively building interactivity in visualisations.
Vega provides a rich set of interaction features which can be combined to perform tasks such as brushing and
linking, but these features come at the cost of a more complex language for designing the visualizations
themselves. In contrast, whilst our work provides a includes a more limited set of interaction features,
these are contained within the language itself, rather than forcing the user to build their own} it
frees up the developer to focus on building their data analysis programs, leaving the burden of implementing
selections to the language itself. \JBnote{Both \citet{north00} and \citet{livny97} are similar in spirit
to our work, describing systems for building interactive visualisations out of relational databases,
modelling them with database schema and relational queries respectively. In both cases, their systems are
limited to operating over relational database models, whereas our own work can be applied to data of any shape,
provided it is supported by our language.}

\JBnote{Glue \cite{beaumont13} is a python library for building linked visualisations for scientific applications.
Glue's main advantage is its graphical user interface, allowing the user to build their visualisations via drag-and-drop
rather than writing code, and to build complex interactions over the top of their visualisation. This broad scope
comes at the cost of a complex user interface, as opposed to our own work, where limiting the focus of interaction
to discovering data dependencies allows us to provide a tighter, simpler interface. Spurious(??)}

\subsection{Transparent research outputs}

\citet{dragicevic19} also develop techniques for transparent research outputs, via explorable multiverse
analysis, exposing \emph{analysis parameters}, the methodological choices made in designing a data analysis.
Since different choices made in design will impact the conclusions of the analysis, they exposes the choices
made to users, and allows them to toggle between possible choices at given points in the analysis, observing
how they impact the results. We view our work as complementary to theirs, since we are more concerned with the
dependencies observed within a specific choice of analysis parameters, rather than the choices themselves.
Toggling choices in their interactive artifacts updates the artifact globally, and it can be different to know
the exact impact that one of these analysis parameters has on results. It seems reasonable to package our
dependency analysis alongside such a multiverse analysis, allowing the user to observe the dependencies on a
methodological choice, as well as the underlying data dependencies used in the analysis.
