\section{Related work}
\label{sec:related-work}

\subsection{Data Provenance}

There is a long history of provenance techniques, ranging from coarse-grained (document-level) provenance
tracking [...] to fine-grained database provenance [...]. In terms of fine-grained techniques for structured
outputs like visualisations, the two main areas of prior work are [psallidas] for query languages, and
[perera] for general-purpose languages.

\cite{dietrich22} attempts to simultaneously explain both value and control dependencies in recursive database
queries and user-defined functions. Their work takes SQL queries, and rewrites them into a pairs of queries
which compute not only the output table, but the provenance of the values it contains.

\JBnote{In \cite{fehrenbach19}, the authors present a system for language-integrated data provenance for the
LINKS programming language \cite{cooper06}. Their system is rooted in the nested relational calculus
(NRC)~\cite{BUNEMAN19953}, and -- despite integration with a general purpose language -- only supports
provenance queries for an embedded SQL-like language, rather than dependency queries over the more general
constructs in LINKS. Extending our work to support similar provenance queries would require revisiting the
dependency relation, since we do not distinguish between control-flow -- coming from an if-else or a pattern
match -- and value dependencies -- from producing new values out of old ones. This information roughly
corresponds to the ``why'' and ``where'' provenance described in the database setting. We would also need to
consider how SQL queries and the NRC differ semantically from our core functional calculus.}

\subsection{Dynamic Dependence Graphs}

Dynamic dependence graphs have been used extensively for program slicing \cite{field98,hammer06}, optimisation
\cite{ferrante87}, incremental computation \cite{acar02} and fault localisation~\citet{Soremekun2021}. Most of
these applications are for imperative languages, where it is useful distinguish between control and data
edges; because \OurLang is pure, we use somewhat simpler dependence graphs with a single kind of edge. However
different kinds of edge are likely to be needed for future applications (\secref{future}). The main
contribution of our work to the dependence graph paradigm are our cognacy operators, which allow the
identification of minimally related sets of inputs ($\relInputR$) and minimally related sets of outputs
($\relOutputR$), in a formal setting where we show these operators to be ``self-conjugate'' and related to
Galois connections.

\subsection{Galois Slicing}

Although we do not consider program slices in the present work, our formal setting is closely related to
program slicing techniques based on Galois connections \cite{perera12a,perera16d,ricciotti17}. In these works,
which use a bidirectional interpreter, the forward and backward directions of the interpreter correspond to
our \emph{sufficiency} ($\sufficesR$) and \emph{demands} ($\demandsR$) queries. \citet{perera22} extended this
approach to a setting where slices have complements, and showed how composing the backward analysis with the
De Morgan dual of the forward can be used to implement linked brushing feature commonly used in data
visualisation. As well as requiring a bidirectional interpreter, the main difficulty with this approach has
been achieving interactive performance. To provide the bidirectional interpreter, implementations have relied
on a sequential execution trace, used in the forwards direction to ``replay'' the computation, propagating
sufficiency information from inputs to outputs, and in the backwards direction to ``rewind'' the computation,
propagating demand from outputs to inputs. As discussed in \secref{evaluation}, and in contrast to the graph
approach presented here, this sequential approach is unable to exploit the very independence that makes
slicing useful in the first place.

\subsection{Linked Visualisations}

The connection between visual selection (such as clicking or lasooing) and data ``selection'' has been
explored in the data visualisation literature, leading to various techniques for inverting selections in
visual space to obtain selections in the underlying data~\cite{north00, heer08}. There is also a substantial
literature on linked brushing~\cite{becker87, livny97} as a way of connecting output selections via mediating
data selections. Although this has long been recognised as an important visual tool, with \citet{roberts06}
arguing it should be ubiquitous, there has been relatively little work in general-purpose infrastructure to
support it. For example Reactive Vega~\cite{satyanarayan17} provides a rich set of interactivity features to
support linked brushing, but no mechanism for automatically propagating selections through arbitrary
intervening queries. Glue \cite{beaumont13} is a powerful Python library for building linked visualisations
for scientific applications, but the developer is responsible for specifying the relationships between data
sets that unpin the linking. More infrastructural approaches to linked brushing
\cite{north00,livny97,psallidas18smoke}, similar in spirit to our work, have been developed mainly for
relational languages for data visualisation. Relational languages are a promising direction in data
visualisation, but general-purpose languages continue to be widely used too, so it is important to support
linked brushing in this context as well.

\subsection{Transparent research outputs}

\citet{dragicevic19} also develop techniques for transparent research outputs, via explorable multiverse
analysis, exposing \emph{analysis parameters}, the methodological choices made in designing a data analysis.
Since different choices made in design will impact the conclusions of the analysis, they expose these choices
to users, and allow them to switch between different choices at key points in the analysis so they can observe
how they impact the results. Our work is potentially complementary to this line of research: we are concerned
with surfacing the dependencies that arise within a specific choice of analysis parameters, whereas multiverse
analyses are about exploring how those dependencies might change under a different set of the choices. Making
a different choice in one of their interactive artifacts updates the artifact globally, and it can be
different to know the exact impact that one of those analysis parameters has on results; it might be useful to
package our dependency analysis alongside such a multiverse analysis, allowing the user to observe the
dependencies on a methodological choice, as well as the underlying data dependencies used in the analysis.
