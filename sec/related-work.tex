\subsection{Applying Dynamic Dependence Graphs}

We are not the first to consider using dynamic dependence graphs for functional
programming languages. For example, the compilation of a functional
program to a graph has been used to implement incremental evaluation of programs in \citet{acar02, acar06b}.
In contrast to their work, which focusses on efficiently propagating changes for inputs to computations, we
are concerned with the implementation of interactive data exploration systems.
%Additionally their work is
%implemented as a library for Standard ML in contrast to our implementation existing
%as a built for purpose programming language.

For a more generic perspective on program slicing, \citet{field98} consider dynamic dependence tracking in
term-rewriting systems. Their approach allows them to perform graphical program slicing on a subset of Pascal,
but differs from our work in two ways. Firstly, they are concerned primarily with program slicing
of imperative programs as opposed to building interactive visualizations, and secondly,
they explicitly represent reduction steps in their dependence graphs. In
contrast, we do not represent this sort of information in the graph at all, and instead of
representing the semantics as a term-rewriting system, we present ours as 
an extended big-step relation.

More recently there has been a body of work aimed at using dynamic dependence graphs
to assist in program fault localization, but again these are not focussed on
interactive visualization systems, but rather on bug finding in programs.
For a survey see \citet{Soremekun2021}.

\subsection{Galois Slicing}

Galois connections between lattices offer an appealing mathematical foundation for bidirectional dynamic
program analysis, cleanly characterising input-output relationships in terms of demand and sufficiency
\cite{perera12a,perera16d,ricciotti17}. In these works, Galois connections are
applied to the problem of program slicing. The upper adjoint -- which characterises
forward slicing from inputs to outputs -- can be thought of as a \emph{sufficiency} operator,
picking out all the outputs which can be computed using only a particular set of
inputs; the lower adjoint, which characterises backward slicing, is a \emph{demand} operator, picking out the
specific inputs needed to compute a particular set of outputs. \citet{perera22} extended this approach to a
setting where slices have complements and the slices of a particular program or value form a Boolean lattice;
they then showed how the De Morgan dual of the upper adjoint can be used to pick out \emph{linked outputs},
namely the other outputs that ``compete'' with a given set of outputs in the sense of demanding some of the
same inputs, and proposed this as a framework for understanding the ``brushing and linking'' feature commonly
used in data visualisation.

However, implementations of Galois slicing efficient enough to support the kind of interactive applications
considered here have proved elusive. To compute the two analyses, implementations have relied on a sequential
execution record, usually taking the form of a big-step or small-step trace. The forward analysis uses the
trace to ``replay'' the computation, propagating information about resource availability from inputs to
outputs; the backwards analysis uses the trace to ``rewind'' the computation, propagating information about
demand from outputs to inputs. This overly sequential approach makes the approach unable to exploit the very
independence that makes slicing useful in the first place. Moreover, the backwards analysis makes frequent use
of lattice join ($\join$) to combine slicing information computed along different branches of the computation.
Joining closure slices in particular becomes expensive because of the contained environments (which in turn
contain closures), and these issues have made the approach prohibitively slow for interactive use. Compared to
Galois slicing, our approach of decomposing the problem into a graphical semantics and a pair of analyses over the graph
significantly reduces the implementation burden on the developer, since the algorithms for the program analyses
are language-agnostic and thus only need to be implemented once.

\subsection{Interactive Visualization}
\JBnote{Start of change}
We are not the first to consider shifting the burden of interactive visualizations
into the language runtime. Reactive Vega \citet{satyanarayan17},
presents a system for building interactivity in visualizations. 
Vega is a declarative DSL for constructing interactions with visualizations.
The features of Vega allow for more complicated interactions than our own
work at present, however these are hampered by requiring the designer to learn
multiple separate languages. Further, the syntax of Vega for combining these
interactions is non-obvious to a new user. In contrast, whilst our work provides
a smaller set of interaction primitives it frees up the developer to focus on
building their data analysis programs, leaving the burden of implementing selections
to the language itself. The benefit of including everything into the base language
is that it reduces the number of tools that a developer needs proficiency with.
 In future work it could be beneficial to provide more
ways for a Fluid user to combine their selections, such as ranges and marquee
selections, however we do not consider this to be our primary focus.
\JBnote{end of change}
Our linking of visualizations is similar in spirit to the work of \citet{north00}.
In that work, the authors design a modular system for replacing visualizations of
databases. Their system is modelled by relational database schema, and is designed
to facilitate interactions with these modular visualizations, but is
limited to data from relational databases, whereas ours can be applied to data
of any shape, as long as it is supported by our language.
Devise \citet{livny97} is another visualization framework for building
interactive visualizations of relational database tables. Similar to \citet{north00},
their work is defined by its usage of relational databases, and the way they
create a semantics for queries on visualizations using the model of relational
database queries. 
\JBnote{Database Provenance}
Recent work in database provenance \citet{dietrich22} attempts to simultaneously
explain both value and control dependencies in recursive queries and user-defined
functions. Their work takes an SQL query and rewrites it into a pair of queries
which compute not only the output table, but the provenance of the values it contains.
\JBnote{currently discussing including where versus why here, but could be moved to
section 7}
In order to modify our approach to work in this setting, we would need to encode
extra information into the edges of the graph, specifically whether an edge is
a control-flow edge -- coming from an if-else or a pattern match -- or a value
edge -- from producing a new value out of old ones. This information roughly
corresponds to the "why" and "where" provenance described in the database setting.
Further we would need to use a dependency relation which agrees with the semantics
of an SQL query or user-defined functions, since a relational database is
semantically distinct from our functional setting.
