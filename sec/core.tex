\section{A Core Language with Graphical Syntax and Semantics}
\label{sec:core}

In \secref{conjugate}, we defined the abstract setting of dependence graphs and conjugate operators \emph{demands} ($\demandR$) and \emph{demanded by} ($\demandByR$) over such graphs.
% using this to derive sets of related inputs and related outputs.
This section shows how we implement that graphical abstraction for \OurLang -- an untyped pure functional programming language, used to generate the scatter plots in \secref{example}; an example of a program in \OurLang is \figref{energy-query}, which is the source code behind those plots. We first introduce the syntax of our core language constructs (\secref{core:syntax}). Then we define a
big-step operational semantics that simultaneously (i) evaluates a term to a value and (ii) constructs an accompanying
dependence graph for the evaluation of that term (\secref{core:semantics}); we also address how we deal with pattern-matching and mutual recursion.

\subsubsection{Terms}
\label{sec:core:expressions}

\figref{syntax} defines the \emph{terms} $e$ of the language mutually inductively with \emph{raw terms} $\raw{e}$, pairing those $\raw{e}$'s with an address $\alpha$. These addresses, explained in \todo{forward-ref}, will (later) form the vertices of the graphs that we build in the graph semantics.
%, and can be implemented as any identifier that uniquely identifies (parts of) a term  (our specific implementation uses an integer counter for generating fresh vertices). %The other language construct that corresponds to vertices are values $v$.


Raw terms $\raw{e}$ include integer constants ranged over by $n, m$%
; variables ranged over by $x, y, f$%
; let-bindings $\exLet{x}{e}{e'}$%
; record construction $\exRec{\seq{\bind{x}{e}}}$%, using the notation of \defref{finite-map}% for mapping variables to terms
; and record projection $\exRecProj{e}{x}$. % for accessing variable $x$ in record $e$
We also have constructor expressions $\exConstr{c}{\seq{e}}$, where $c$ ranges over data constructors and is fully
saturated by arguments $\seq{e}$; we write $\datatype{c} = n$ to denote that $c$ takes $n \in \mathbb{N}$ arguments.

Application comes in two forms:  standard application $\exApp{e}{e'}$, and \emph{foreign application} $\exForeignApp{f}{\seq{e}}$ for calling foreign functions which are explained in \secref{core:foreign}. The last two terms define anonymous functions $\exFun{\sigma}$ and (mutually) recursive let-bindings $\exLetRecElim{\seq{x : \sigma}}{e}$, where $\sigma$ is a pattern-matching construct called an \emph{eliminator} detailed further in \secref{core:continuations}.

\subsubsection{Foreign functions}
\label{sec:core:foreign}
The language is parameterised by a finite map $\Phi(f) = n$ from variables $f$ to the arities $n \in \Nat$ of the
foreign function they represent (analogous to $\Sigma(c) = n$ for constructors). A crucial specification of foreign functions, for the graph semantics later, is that each provides an interpretation that computes both the function's result and a suitable dependence graph.

Foreign functions \emph{per se} are not first-class and calls $\exForeignApp{f}{\seq{e}}$ are saturated,
i.e.~$\length{\seq{e}} = \Phi{(f)}$. First-class foreign functions are provided via a top-level environment
which maps every ${f}$ to the closure
$\exClosure{\envEmpty}{\seqEmpty}{\elimVar{x_1}{\elimVar{\iter}{\elimVar{x_{\Phi{(f)}}}{\exForeignApp{f}{\seq{x}}}}}}$
where $\length{\seq{x}} = \Phi{(f)}$. Saturated calls are only part of the core language and user programs
instead use the first-class representation.

\subsubsection{Continuations and eliminators}
\label{sec:core:continuations}
A \emph{continuation} $\kappa$ describes how an execution proceeds after a value is pattern-matched, and is
either a term $e$ or an \textit{eliminator} $\sigma$. Eliminators are
trie-like objects \cite{hinze00} which can serve as a plausible desugaring target for surface-language pattern-matching
constructs. (\citet{peytonjones2021} present a similar idea.) An eliminator specifies
how to pattern-match a value and then select a continuation $\kappa$ to be executed under additional variable bindings. A
variable eliminator $\elimVar{x}{\kappa}$ says how to match any value (as  variable $x$) and continue as $\kappa$. A record
eliminator $\elimRecord{\seq{x}}{\kappa}$ says how to match a record with fields $\seq{x}$, and provides
a continuation $\kappa$ for matching the values of those fields. Lastly, the eliminator $\elimConstr{\seq{c \mapsto
\sigma}}$ for constructors provides a branch $c \mapsto \sigma$ for each constructor $c$ in
$\seq{c}$, where each $\sigma$ specifies how the arguments to  $c$  will be matched.
(We assume these constructors come from the same data type, but this is not enforced in the core language.)

\subsubsection{Values and environments}
\label{sec:core:values}

Values $v$ include integers $n, m$, records  $\exRecord{\seq{x \mapsto v}}$ and constructor values
$\exConstr{c}{\seq{v}}$. We also define function closures as $\exClosure{\gamma}{\rho}{\sigma}$ where $\sigma$
is the function (eliminator), $\gamma$ is its environment, and to support mutual recursion,  ${\rho}$ is the
(possibly empty) environment of functions (eliminators) with which $\sigma$ was mutually~defined. An
environment is defined as a finite~map.

\subsection{Evaluation and graph construction}
\label{sec:core:semantics}

\subsubsection{Pattern matching}

\figref{core:pattern-matching} defines the pattern-matching judgement $\seq{v}, \kappa \match \gamma, e, V$.
Rather than matching a single value $v$ against an eliminator $\sigma$, the judgement matches a ``{stack}'' of values $\seq{v}$ against a continuation $\kappa$.
It then returns the selected branch $e$, an environment $\gamma$ providing bindings for the free variables in $e$, and a set $V$ of vertices found in the matched portions of $\seq{v}$.

The $\match$-done rule expresses exactly when using a \emph{term} $e$ as the continuation may succeed: when the stack of values to be matched is empty, and so $e$ is treated as the selected term to be executed. The other rules require an \emph{eliminator} $\sigma$ as the continuation -- using this to match the head of a non-empty stack $v \cons \seq{v}$, unpack any relevant subvalues, and then push them onto the tail $\seq{v}$ to be recursively matched by the selected continuation  inside $\sigma$.

\begin{definition}[Vertices of a term]
\label{def:core:vertices}
Define $\V(e)$ as the set of vertices $\alpha$ that occur anywhere in a term~$e$, and similarly for values $v$ and eliminators $\sigma$.
\end{definition}

A variable eliminator $\elimVar{x}{\kappa}$ matches any value $v$ and returns all the vertices $\V(v)$ embedded in $v$, denoting \todo{need to clarify...}. The eliminator $\elimRecord{\seq{y}}{\kappa}$
only matches with a record $\annot{\exRec{\seq{\bind{x}{v}}}}{\alpha}$  if the variables
in $\seq{y}$ are also fields in $\seq{x}$, returning the (top-level) vertex $\alpha$ associated with the  record; the condition is enforced by  $\exRec{\seq{\bind{y}{u}}}
\subseteq \exRec{\seq{\bind{x}{v}}}$ which simultaneously projects out the corresponding values of
 $\seq{u}$ from $\seq{v}$. Lastly, an eliminator with a branch $(\elimBind{c}{\kappa})$
only matches a value $\annot{\exConstr{c}{\seq{v}}}{\alpha}$ constructed by $c$, and returns the vertex $\alpha$ associated with that particular instance of $c$.

\subsubsection{Evaluation }
\figref{core:eval} defines a big-step evaluation relation $\gamma, e, V \evalS G, v$ for the core language.
This states that term $e$ under environment $\gamma$ evaluates to a value $v$ plus dependence graph $G$; the
vertex set $V$ corresponds to the inputs consumed by the current active function call from which $e$ is being evaluated. \todo{refine} The set $V$ is initially empty for a top-level program $e$, and grows via the output of the pattern-matching judgement $\seq{v}, \kappa \match \gamma, e, V$ which is invoked when a function is applied to an argument.
 The relation $\gamma, \seq{e}, V \evalS G,
\seq{v}$ is similar but for a sequence of terms $\seq{e}$; its single rule evaluates each term $e_i \in
\seq{e}$ to a value in $v_i \in \seq{v}$, and constructs a dependence graph that is the disjoint union of
graphs produced by each individual evaluation. For convenience, we will use notation $\bind{\alpha}{V}$ in
\defref{outgoing-edges} for adding a new vertex $\alpha$ and its dependencies $V$ to a graph.

\begin{definition}[Outgoing edges]\label{def:outgoing-edges}
   For vertex $\alpha$ and set of vertices $V$, define $\bind{\alpha}{V}$ as a set of edges from $\alpha$ to all vertices in $V$.
 %   \DOnote{Is this the best notation? If we are thinking of edges from $V$ to $\alpha$ then it feels like the notation should reflect that ordering?}
\end{definition}


The rule for integers $n_\alpha$ simply returns their value form $n_{\alpha'}$ but as a fresh vertex
$\alpha'$. The resulting dependence graph $\set{\bind{\alpha'}{\alpha \cons V}}$ then contains a vertex
$\alpha'$ with outgoing edges to all vertices in $\alpha \cons V$, expressing that evaluating to  $n_\alpha'$
depended on the original term $n_\alpha$ alongside any other inputs that were found in $V$. Variable
evaluation is standard, and the returned dependence graph is empty due to no new vertices being constructed
from simply looking up values. Evaluation of an anonymous function $\exFun{\sigma}$ constructs the closure
$\exClosure{\gamma}{\envEmpty}{\sigma}_\alpha$ as a new vertex, capturing the current environment $\gamma$ and
using $\envEmpty$ as the set of associated mutually recursive definitions.

The rule for records $\annRec{\seq{\bind{x}{e}}}{\alpha}$ evaluates the sequence of terms $\seq{e}$ associated
with its fields to $\seq{v}$, returning  value $\annRec{\seq{\bind{x}{v}}}{\alpha'}$ as a fresh vertex
$\alpha'$; the dependence graph is then the dependencies of each $v_i \in v$ along with the dependencies of
$\annRec{\seq{\bind{x}{v}}}{\alpha'}$. Record projection $e.y$ uses the previous rule to evaluate the entire
record $e$ before looking up the value for $y$; as the record value as a whole structure goes unused, its
vertex is omitted in the dependence graph. Evaluation of constructor expressions $c(\seq{e})_\alpha$ and
foreign function calls $f(\seq{e})$ is similar to that of records, but also coincides the
arity of $c$ or $f$ with the number of arguments in $\seq{e}$. For foreign calls, $\hat{f}$ is the
foreign implementation that provides a way to evaluate the calling of  $f$ to a graph and value, as we required  in \secref{core:foreign}.


Application $\exApp{e}{e'}$ is more involved, dealing with both mutual recursion and pattern-matching. First
we obtain the recursive definitions $\rho$ from the closure $\annClosure{\gamma_1}{\rho}{\sigma}{\alpha}$
computed by function $e$, before using the auxiliary relation $\closeDefs$ (bot. \figref{core:eval}) to
promote $\rho$ to an environment of closures. This is done by enumerating over each definition $\rho(x_i) \in
\rho$ and lifting it into its own closure $(\gamma_1, \rho, \rho(x_i))_{\alpha_i}$ as a fresh vertex
${\alpha_i}$, capturing $\rho$ and a copy of the original environment $\gamma_1$; the graph produced by
$\closeDefs$ is then the disjoint union of dependencies for each of these new closures. Second, we use the
pattern-matching relation $\match$ (\figref{core:pattern-matching}) to match the value $v'$ computed by
argument $e'$ against $\sigma$; what is returned, includes the selected term $e^\twoPrime$ to be executed and
the vertices $V'$ which arriving at  $e^\twoPrime$ depended on. The last premise evaluates $e^\twoPrime$ to a
final value, where its input set of vertices $\alpha \cons V'$ denotes a dependency on the original closure
and the value(s) that were matched. As usual, the overall dependence graph is the combination of the ones
constructed by each intermediate step.

Finally, the rule for regular let-bindings $\exLet{x}{e}{e'}$ is standard and graph construction is simply the disjoint union of graphs of $e$ and  $e'$. The case for recursive let-bindings $\exLetRec{\seq{\bind{x}{\sigma}}}{e}$ is the same except requiring $\closeDefs$ to evaluate the  mutually recursive definitions $\seq{\bind{x}{\sigma}}$, as was explained for~application.
