\section{A Core Language with Graphical Syntax and Semantics}
\label{sec:core}

In \secref{conjugate}, we defined the abstract setting of dependence graphs and conjugate operators
\emph{demands} ($\demandsR$) and \emph{demanded by} ($\demandedByR$) over such graphs. We now implement that
graphical abstraction for \OurLang, an untyped, pure functional programming language. This core calculus we
go on to describe is what underlies the surface-language programs such as \figref{overview:energy-query}, used
to generate and analyse the scatter plots from earlier. We first introduce the syntax of our core language
constructs (\secref{core:syntax}). Then we define a big-step operational semantics that simultaneously (i)
evaluates a term to a value and (ii) constructs an accompanying dependence graph for the evaluation of that
term (\secref{core:semantics}); we also address how we deal with pattern-matching and mutual recursion.

\subsubsection{Terms}
\label{sec:core:expressions}

\figref{syntax} defines the expressions $e$ of the language, which include variables $x, y, f$%
; integer constants $n, m$%
; let-bindings $\exLet{x}{e}{e'}$%
; record construction $\exRec{\seq{\bind{x}{e}}}$%
; and record projection $\exRecProj{e}{x}$. We also have constructor expressions $\exConstr{c}{\seq{e}}$,
where $c$ ranges over data constructors and is fully saturated by arguments $\seq{e}$; we write $\datatype{c}
= n$ to denote that $c$ takes $n \in \mathbb{N}$ arguments. Application comes in two forms: standard
application $\exApp{e}{e'}$, and \emph{foreign application} $\exForeignApp{f}{\seq{e}}$ for calling foreign
functions which are explained in \secref{core:foreign}. The last two terms define anonymous functions
$\exFun{\sigma}$ and (mutually) recursive let-bindings $\exLetRecElim{\seq{x : \sigma}}{e}$, where $\sigma$ is
a pattern-matching construct called an \emph{eliminator} detailed further in \secref{core:continuations}.

\subsubsection{Foreign functions}
\label{sec:core:foreign}
The language is parameterised by a finite map $\Phi(f) = n$ from variables $f$ to the arities $n \in \Nat$ of
the foreign function they represent (analogous to $\Sigma(c) = n$ for constructors). For the graph semantics
that will follow, every foreign function $f$ is required to provide an interpretation $\interpret{f}$ that
computes both $f$'s result and a suitable dependence graph.

Foreign functions in the core language are not first-class and calls $\exForeignApp{f}{\seq{e}}$ are
saturated, i.e.~$\length{\seq{e}} = \Phi{(f)}$. In our implementation, which also provides a surface language
which desugars into the core, first-class foreign functions are supported via a top-level environment which
maps every ${f}$ to the closure
$\exClosure{\envEmpty}{\seqEmpty}{\elimVar{x_1}{\elimVar{\iter}{\elimVar{x_{\Phi{(f)}}}{\exForeignApp{f}{\seq{x}}}}}}$
where $\length{\seq{x}} = \Phi{(f)}$.

\subsubsection{Continuations and eliminators}
\label{sec:core:continuations}
A \emph{continuation} $\kappa$ describes how an execution proceeds after a value is pattern-matched, and is
either a term $e$ or an \textit{eliminator} $\sigma$. Eliminators are
trie-like objects \cite{hinze00} that specify
how this pattern-matching is done and the subsequent continuation $\kappa$ to be executed under additional variable bindings. (These are what the piecewise function definitions of our surface-language, e.g. \lstinline{plot} in \figref{overview:energy-query}, desugar into; \citet{peytonjones2021} present a similar idea.)
\edit{The use of eliminators in our language is a design decision, and was not informed by our dependency analysis. The ideas we have
presented can be readily applied to a language based on a more traditional lambda calculus using a different 
approach to pattern matching.}

A variable eliminator $\elimVar{x}{\kappa}$ says how to match any value (as  variable $x$) and continue as $\kappa$. A record
eliminator $\elimRecord{\seq{x}}{\kappa}$ says how to match a record with fields $\seq{x}$, and provides
a continuation $\kappa$ for matching the values of those fields. Lastly, the eliminator $\elimConstr{\seq{c \mapsto
\kappa}}$ provides a branch $c \mapsto \kappa$ for each constructor $c$ in
$\seq{c}$, where each $\kappa$ may specify how the arguments to  $c$  will be matched.
(We assume that any constructors matched by an eliminator all belong to the same data type, but this is not enforced in the core language.)

\subsubsection{Addresses for partial values}
\label{sec:core:addresses}
The addresses $\alpha$ that annotate values act as identifiers, uniquely corresponding those values to
specific vertices in a dependence graph. There are many sensible ways of assigning addresses (our particular
implementation uses an integer counter to generate new ones) as long as some freshness condition is satisfied
-- ensuring that there are no unwanted address collisions in a given value i.e. graph. For simplicity, we
elide this side-condition in the graph semantics (next) and assume it is met whenever a new address $\alpha$
is introduced.

\subsubsection{Pattern matching}
\label{sec:core:semantics:pattern-matching}
\figref{core:pattern-matching} defines the pattern-matching judgement $\seq{v}, \kappa \match \gamma, e, V$.
Rather than matching a single value $v$ against an eliminator $\sigma$, the judgement matches a ``{stack}'' of values $\seq{v}$ against a continuation $\kappa$.
It then returns the selected branch $e$, an environment $\gamma$ providing bindings for the free variables in $e$, and a set $V$ of vertices found in the matched portions of $\seq{v}$.

The \ruleName{$\match$-done} rule expresses exactly when using a \emph{term} $e$ as the continuation may succeed: when the stack of values to be matched is empty, and so $e$ is treated as the selected term to be executed. The other rules require an \emph{eliminator} $\sigma$ as the continuation -- using this to match the head of a non-empty stack $v \cons \seq{v}$, unpack any of its relevant subvalues, and then push them onto the tail $\seq{v}$ to be recursively matched by the continuation selected in $\sigma$.

A variable eliminator $\elimVar{x}{\kappa}$ matches any value $v$ and returns no vertices, reflecting the fact that no part of $v$ would need to be consumed to select $\kappa$ as the continuation. The eliminator $\elimRecord{\seq{y}}{\kappa}$
only matches with a record $\annot{\exRec{\seq{\bind{x}{v}}}}{\alpha}$  if the variables
in $\seq{y}$ are also fields in $\seq{x}$, returning the vertex $\alpha$ associated with the record; this condition is specified by the premise $\exRec{\seq{\bind{y}{u}}} \subseteq \exRec{\seq{\bind{x}{v}}}$, which simultaneously projects out the corresponding values of
 $\seq{u}$ from $\seq{v}$. Lastly, an eliminator with a branch $(\elimBind{c}{\kappa})$
only matches a value $\annot{\exConstr{c}{\seq{v}}}{\alpha}$  constructed by $c$, and returns the vertex $\alpha$ associated with that particular instance of $c$.


\subsubsection{Evaluation}
\figref{core:eval} defines a big-step evaluation relation $\gamma, e, V \evalS v, G$ for the core language,
stating that term $e$, under an environment $\gamma$ and vertex set $V$, evaluates to a value $v$ plus dependence graph~$G$. The input set $V$ corresponds to the inputs consumed by the current active function call from which $e$ is being evaluated, and can be thought of as the ``ambient'' set of  dependencies; this is initially empty for a top-level term, and may grow whenever a function is applied to an argument and pattern-matching occurs (i.e. in the \ruleName{$\evalS$-app} rule, which we explain later). The output graph $G$ is built by specifying new graph fragments and then combining them; for convenience, we write $\inStar{V}{\alpha}$ as shorthand for the star graph $(\set{\alpha} \cup V, V \times \set{\alpha})$ indicating that vertex $\alpha$ depends on all vertices in $V$.

The \ruleName{$\evalS$-var} rule for evaluating variables is standard, and the returned dependence graph is empty; that is, no new vertices are constructed
as a result of simply looking up values. Most of the other evaluation rules can generally be understood in terms of two recurring patterns.

First, for any introduction rule that creates a new (partial) value, there is no choice but to allocate that
value with a new vertex (address) which depends on ambient vertices $V$. These cases include
\ruleName{$\evalS$-int}, \ruleName{$\evalS$-function}, \ruleName{$\evalS$-record}, and
\ruleName{$\evalS$-constr}. For example, \ruleName{$\evalS$-int} evaluates an integer $n$ to its value form
$n_{\alpha}$ assigned a fresh vertex $\alpha$; the resulting dependence graph is then
$\set{\bind{\alpha}{V}}$, denoting that evaluating to  $n_\alpha$ depended on any inputs that were found in
$V$. Likewise, \ruleName{$\evalS$-function} evaluates an anonymous function $\exFun{\sigma}$ by constructing
the closure $\exClosure{\gamma}{\envEmpty}{\sigma}_\alpha$ annotated by a new vertex $\alpha$; here, the
closure captures the current environment $\gamma$ and uses $\envEmpty$ as the set of mutually recursive
definitions. The ``exception'' to this pattern is \ruleName{$\evalS$-record-project} for $e.y$, which
evaluates a record $e$ to  $\annRec{\seq{\bind{x}{v}} \cons (\bind{y}{u})}{\alpha}$ before returning the value
$u$ associated to field $y$; while this indeed introduces a record value allocated with a new vertex $\alpha$,
the record as a whole goes unused, and so $\alpha$ is omitted in the final dependence~graph.

The second recurring pattern is that, for any rule which involves evaluating subterms (of a term), the
corresponding subgraphs that are constructed must be disjoint -- reflecting that there is no overlap between
their vertex addresses -- and their union is the dependence graph of the overall term.  This general principle
is captured by the auxiliary evaluation relation $\gamma, \seq{e}, V \evalS \seq{v}, G$ (bottom of
\figref{core:eval}), which is for evaluating a sequence of terms $\seq{e}$. Its single rule evaluates each
term $e_i \in \seq{e}$ to a value $v_i \in \seq{v}$ and graph $G_i \in \seq{G}$, and builds the dependence
graph $\textstyle{\bigdisjunion} \seq{G}$. We make use of  this relation in the rules
\ruleName{$\evalS$-record} for $\exRec{\seq{\bind{x}{e}}}$, \ruleName{$\evalS$-constr} for $c(\seq{e})$, and
\ruleName{$\evalS$-foreign-app} for $f(\seq{e})$, which all involve evaluating a sequence $\seq{e}$ of
subterms; in the last rule, $\hat{f}$ is the

Of course, this pattern applies to subterms in general and not just those expressed as a sequence $\seq{e}$. For example, the  \ruleName{$\evalS$-let}  rule for $\exLet{x}{e}{e'}$ (which otherwise behaves as standard) simply unions the graphs of subterms $e$ and~$e'$, and similarly for  \ruleName{$\evalS$-let-rec} and  \ruleName{$\evalS$-app}.

To fully explain the last two rules, \ruleName{$\evalS$-let-rec} and  \ruleName{$\evalS$-app}, we first detail how our language deals with \emph{mutual recursion}. For this,  \figref{core:close-defs} defines the auxiliary relation $\gamma, \rho, V \closeDefs \gamma', G$, which takes an environment  $\rho$ of recursive definitions and evaluates it to a value environment $\gamma'$ of closures, while also building a dependence graph $G$. This works by turning each function definition $\rho(x_i) \in \rho$ into a newly allocated closure $(\gamma, \rho, \rho(x_i))_{\alpha_i}$ as a fresh vertex ${\alpha_i}$, capturing $\rho$ and a copy of the original environment $\gamma$, where each closure depends on ambient inputs $V$ (like in evaluation). The final dependence graph is the combination of each closure's subgraph (also like in evaluation).

Returning to \figref{core:eval}, rule \ruleName{$\evalS$-let-rec}  for  $\exLetRec{\seq{\bind{x}{\sigma}}}{e}$ is then the same as regular let-bindings, except using $\closeDefs$ to evaluate  recursive definitions $\seq{\bind{x}{\sigma}}$. The final rule, \ruleName{$\evalS$-app} for $\exApp{e}{e'}$, is especially important to the graph semantics, as it is during application that we grow the ambient inputs $V$  that a given evaluation step depends on. Here, we compute the closure $\annClosure{\gamma_1}{\rho}{\sigma}{\alpha}$ of function $e$% (and use ($\closeDefs$) to evaluate $\rho$)
, and use its eliminator $\sigma$ to pattern-match against the value $v$' of argument $e'$. What is returned includes (i) the \emph{selected branch} $e^\twoPrime$ and (ii) the vertex set $V'$, where $V'$ represents the values in $v'$ consumed by pattern-matching in order to lead to $e^\twoPrime$. The last premise which executes the branch then specifies its ambient dependencies as $V' \disjunion \set{\alpha}$; that is, the (closure of the) function that was applied, $\alpha$, and the (consumed values of the) argument it was applied to, $V'$.
