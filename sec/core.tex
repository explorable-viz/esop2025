\section{A Core Language for Transparent Research Outputs}
\label{sec:core}

In \secref{conjugate}, we formalised a notion of \emph{demands} ($\demandR$) and \emph{demanded by} ($\demandByR$) as conjugate operators, and showed how these could be used to derive sets of related inputs and related outputs in the setting of dependence graphs. This section shifts to the setting of programs, showing how to represent (parts of) programs as vertices in a graph. In particular, we present an core functional language whose operational semantics pairs each program and output with an accompanying dependence graph,  allowing the user to automatically compute $\demandR$ and $\demandByR$.

\subsection{Syntax and graph terms}

\input{fig/core/syntax}

\begin{definition}[Vertices of a term]
\label{def:core:vertices}
Define $\V(e)$ as the set of vertices $\alpha$ that occur anywhere in~$e$.
\end{definition}

We define the graph terms $e$ of the language in \figref{syntax}  as regular terms $\raw{e}$ indexed by a vertex $\alpha$. Concretely, a vertex can be implemented as any identifier that uniquely corresponds (parts of) a term to vertices in a graph (our specific implementation uses an integer counter for generating fresh vertices). The other language constructs that correspond to vertices are values $v$ and patterns $w$;
\defref{core:vertices} then extends to values $v$, patterns $w$, and eliminators $\sigma$, all of which may themselves be vertices and/or contain other entities that are vertices. We introduce these constructs later.


\begin{definition}[Finite map notation]\label{def:finite-map}
   Write $\set{\seq{\bind{k}{v}}}$ to denote a set of pairs $\seqRange{\bind{k_1}{v_1}}{\bind{k_n}{v_n}}$
   where $\seqRange{k_1}{k_n}$ are pairwise unique.
\end{definition}


Regular terms $\raw{e}$ include integers ranged over by $n, m$; variables ranged over by $x, y, f$; let-bindings $\exLet{x}{e}{e'}$%
; record construction $\exRec{\seq{\bind{x}{e}}}$ (\defref{finite-map})% which maps variables to terms (\defref{finite-map})
; record projection $\exRecProj{e}{x}$% for accessing variable $x$ in record $e$
; and data values $\exConstr{c}{\seq{e}}$ where $c$ ranges over data constructors and is fully saturated by arguments $\seq{e}$. A  constructor always inhabits a known data type $D$ and always has the arity $n$ specified by its data type; we write $\datatype{c} = (n, D)$ to denote that $c$ takes $n \in \mathbb{N}$ arguments and constructs a value of data type $D$.

As well as standard application $\exApp{e}{e'}$, we also have \emph{foreign application} $\exForeignApp{f}{\seq{e}}$ for calling foreign functions. The last two terms define anonymous functions $\exFun{\sigma}$ and (mutually) recursive let-bindings $\exLetRecElim{\seq{x : \sigma}}{e}$ where $\sigma$ is a pattern-matching construct called an \emph{eliminator}. We explain eliminators next  and foreign functions in \secref{core:foreign}.


\subsubsection{Continuations, eliminators, and patterns}
\label{sec:core:continuations}
A \emph{continuation} $\kappa$ is either a term $e$ or an \textit{eliminator} $\sigma$. Eliminators are trie-like objects
which can serve as a plausible desugaring target for surface-language pattern-matching constructs.
(\citet{peytonjones2021} present a similar idea in a technical report.) An eliminator matches
against the initial part of a provided value as some pattern $w$, which is either a variable, an integer, record, or data value, and then uses this for selecting a continuation $\kappa$ to be executed. The eliminator for variables $\elimVar{x}{\kappa}$ matches any value and binds it to variable $x$. The record eliminator $\elimRecord{\seq{x}}{\kappa}$ matches a record with fields $\seq{x}$ and binds variables $\seq{x}$ to the components of that record. Lastly, the eliminator for data values $\elimConstr{\seq{c \mapsto \sigma}}$ provides a branch $c \mapsto \sigma$ for each  constructor $c$ of some data type $D$, where each (nested) eliminator $\sigma$ continues by matching against the arguments of that constructor.

\subsubsection{Values}
\label{sec:core:values}

Values $v$ include integers $n, m$; records  $\exRecord{\seq{x \mapsto v}}$; and data values $\exConstr{c}{\seq{v}}$. We also define function closures as $\exClosure{\gamma}{\rho}{\sigma}$ where $\gamma$ is the environment, and to support mutual recursion,  ${\rho}$ is the (possibly empty) environment of functions with which the original function was mutually~defined.

\subsubsection{Foreign functions}
\label{sec:core:foreign}
The language is parameterised by a finite map $\Phi: \Var \to \Nat$ from variables to the arities of the foreign
function they represent. By convention, we use $f$ and $\oplus$ to range over $\dom{\Phi}$. Foreign functions
\emph{per se} are not first-class and calls $\exForeignApp{f}{\seq{e}}$ are saturated, i.e.~$\length{\seq{e}}
= \Phi{(f)}$. First-class foreign functions are provided via a top-level environment which maps every
${f}$ to the closure
$\exClosure{\seqEmpty}{\seqEmpty}{\elimVar{x_1}{\elimVar{\iter}{\elimVar{x_{\Phi{(f)}}}{\exForeignApp{f}{\seq{x}}}}}}$
where $\length{\seq{x}} = \Phi{(f)}$. Although saturated calls are technically part of the language, user programs by convention use the first-class representation.

\subsection{Evaluation and graph construction}

\begin{definition}[Disjoint union of maps]\label{def:disjoint-union}
   For finite maps $m$, $m'$ with $\dom{m} \cap \dom{m'} = \emptyset$, define $m \disjunion m' = m \cup m'$.
\end{definition}

\begin{definition}[Incoming edges]\label{def:incoming-edges}
   For vertex $\alpha$ and set of vertices $V$, define $\bind{\alpha}{V}$ as the set of edges from all vertices in $V$ to $\alpha$.
\end{definition}

We define a big-step evaluation relation $\gamma, e, V \evalS G, v$ for the core language in \figref{core:eval}. This states that program $e$ under environment $\gamma$ evaluates to a value $v$ plus a dependence graph $G$; the  set of vertices $V$ corresponds to the inputs consumed by the current active function call, representing the other, ambient inputs that the evaluation step may also depend on. The relation $\gamma, \seq{e}, V \evalS G, \seq{v}$ is similar but for a sequence of terms $\seq{e}$; its single rule evaluates each term $e_i \in \seq{e}$ to a value in $v_i \in \seq{v}$, and constructs a dependence graph that is the disjoint union (\defref{disjoint-union}) of graphs produced by each individual evaluation. For convenience, we will use  notation $\bind{\alpha}{V}$ (\defref{incoming-edges}) for adding a new vertex $\alpha$ and its dependencies $V$ to a graph.

The rule for integers $n_\alpha$ simply returns their value form $n_{\alpha'}$ but as a fresh vertex $\alpha'$. The resulting dependence graph $\set{\bind{\alpha'}{\alpha \cons V}}$ then contains a vertex $\alpha'$ with incoming edges from all vertices in $\alpha \cdot V$, expressing that evaluating to  $n_\alpha'$ depended on the original term $n_\alpha$ alongside any other inputs that were found in $V$. Variable evaluation is standard, and the returned dependence graph is empty due to no new vertices being constructed from simply looking up~values.
Evaluation of functions $\exFun{\sigma}$ is by using their eliminator $\sigma$ and the current environment $\gamma$ to construct a closure $\exClosure{\gamma}{\varepsilon}{\sigma}_\alpha$ as a new vertex, where environment $\varepsilon$ specifies no available recursive definitions.

The rule for records $\annRec{\seq{\bind{x}{e}}}{\alpha}$ evaluates the sequence of terms $\seq{e}$ associated with its fields to $\seq{v}$, returning  value $\annRec{\seq{\bind{x}{v}}}{\alpha'}$ as a fresh vertex $\alpha'$; the dependence graph is then the dependencies of each $v_i \in v$ along with the dependencies of $\annRec{\seq{\bind{x}{v}}}{\alpha'}$. Record projection $e.y$ uses the previous rule to evaluate the entire record $e$ before looking up the value for $y$; as the record value as a whole structure goes unused, its vertex is omitted in the dependence graph. Evaluation of data values $c(\seq{e})_\alpha$ and foreign function calls $f(\seq{e})$ is similar to that of records, but for the latter, we also require a foreign  implementation $\hat{f}$ of $f$ that provides a way to be evaluated to a graph $G'$ and value $u$.


Application $\exApp{e}{e'}$ is more involved, dealing with both mutual recursion and pattern-matching. First we obtain the recursive definitions $\rho$ from the closure $\annClosure{\gamma_1}{\rho}{\sigma}{\alpha}$ computed by function $e$, before using the auxiliary relation $\closeDefs$ (bot. \figref{core:eval}) to promote $\rho$ to an environment of closures. This is done by enumerating over each definition $\rho(x_i) \in \rho$ and lifting it into its own closure $(\gamma_1, \rho, \rho(x_i))_{\alpha_i}$ as a fresh vertex ${\alpha_i}$, capturing $\rho$ and a copy of the original environment $\gamma_1$; the output graph $G$ is then the disjoint union of dependencies for each of these new closures. Second, we use the pattern-matching relation $\match$ (\figref{core:pattern-matching}) to match the value $v'$ computed by argument $e'$ against $\sigma$. % which returns the bindings arising from the match alongside the selected branch.
The last premise evaluates the body of the matched branch to a final value, where the input set of vertices  $\set{\alpha} \cdot \V(w)$ expresses that arriving at this evaluation step depends on the original closure $\alpha$ and the matched pattern $\V(w)$. As usual, the overall dependence graph is the combination of the ones constructed by each intermediate step.

Finally, the rule for regular let-bindings $\exLet{x}{e}{e'}$ is standard and graph construction is unsurprising, unioning the graphs of $e$ and  $e'$. The case for recursive let-bindings $\exLetRec{\seq{\bind{x}{\sigma}}}{e}$ is the same except requiring $\closeDefs$ to evaluate the environment of mutually recursive definitions $\seq{\bind{x}{\sigma}}$, as explained for~application.

\subsubsection{Pattern matching}

The relation $\seq{v}, \kappa \match \seq{w}, \gamma, e$  in \figref{core:pattern-matching} captures pattern-matching in a slightly unconventional way, by using a \emph{continuation} $\kappa$ to match a \emph{sequence} of values $\seq{v}$ (rather than an eliminator $\sigma$ that matches a single value $v$); it returns the corresponding matched patterns $\seq{w}$, an environment $\gamma$ of variable bindings that arose during the matches, and a term $e$ representing the final branch body to be executed. The ``done'' rule expresses exactly when using a term $e$ as the continuation may succeed i.e. when the sequence of values to be matched is empty, and so $e$ must be the final branch body. The other rules use an eliminator $\sigma$ to match the head of a non-empty sequence $v \cdot \seq{v}'$, and then recurse by using the selected continuation of $\sigma$ to match on the tail $\seq{v}'$.

A variable eliminator $\elimVar{x}{\kappa}$ applied to any value $v$ simply adds  binding $\bind{x}{v}$ to the environment and records $x$ as the matched pattern. An eliminator $\elimRecord{\seq{y}}{\kappa}$ only matches with a record $\annot{\exRec{\seq{\bind{x}{v}}}}{\alpha}$
if the variable names in $\seq{y}$ are also field names in $\seq{x}$; this is enforced by the premise $\exRec{\seq{\bind{y}{u}}} \subseteq \exRec{\seq{\bind{x}{v}}}$ which also coincides those relevant values of $\seq{v}$ with $\seq{u}$. Those fields $\seq{u}$ are then unpacked and matched against, and the rest of original values  matched after.
